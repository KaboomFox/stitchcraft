StitchCraft

VectorCraft integration

How StitchCraft lives inside VectorCraft: what VectorCraft offers today, how we use it without changing VectorCraft (phase 1), what we propose upstream (phase 2), and how an in-tree integration would look (phase 3).

VectorCraft snapshot reviewed: main at 89ea46c (2026-10-08), version 0.6.0, and its plug-in API again at 8bf090b (2026-10-24), after 0.16.0, at v0.17.0 (2026-10-25) and at v0.18.0 (2026-10-28). File references below are to the first unless a version is named. The compatibility gate tests the plug-ins against each VectorCraft release and branch.

2. Extension points that exist today

Plug-in ABI v1 (crates/plugins, docs/plugins.md)

  • Sandbox: a core WebAssembly module run by wasmi 2.0, no imports at all (no WASI, clock, file system or randomness). Exports: memory, vc_abi_version() → 1, vc_manifest(), vc_alloc(size), vc_run(input, len, params, len). Input and output are JSON.
  • Kinds: object filters (read selected paths and compound paths — geometry, fills, strokes, opacity — and return updated or new objects; one undo step) and live effects (rewrite one object’s geometry every time it is drawn, cached by plug-in, parameters and input geometry). From 0.14, exporters write the whole document in a file format of their own, listed by File › Export › Export As.
  • Parameters: manifest schema with number, int, bool, choice; at most 64 parameters (MAX_PARAMS, crates/plugins/src/manifest.rs:11) and a 64 KiB manifest; no labels, units, groups or conditions until 0.14, and the dialog shows the parameters’ names. From 0.14: string and numberList too, up to 256 parameters with at most 64 outside groups, and each parameter’s label, unit, group, help, helpUrl and visibleWhen.
  • Limits (crates/plugins/src/runtime.rs): module ≤ 32 MiB; memory ≤ 512 MiB; output ≤ 64 MiB JSON; fuel 50 M instructions + 4,000 per input byte; wall clock 60 s per filter run and 5 s per live-effect run (crates/plugins/src/effect.rs), with a fresh instance for each call. An export gets 10 G instructions and 300 s (0.14). From 0.17 a filter that declares "budget": "heavy" gets 1 G and 300 s, once the user allows it at install, and runs in the background. From 0.18 a run pays nothing for compiling the functions it calls, which wasmi does at each one’s first call. Before, a first run paid, and could stop with most of its budget left when the 20 M-instruction slice it was in ran out while a function compiled. From M13.2 on, the gate’s Level B found 0.17.0’s command line stopping the PES exporter so on the test sheet TS-04, an export that takes 34 M instructions in 0.18.0’s host.
  • Live-effect input is the object’s geometry: type, path, fillRule, bounds. From 0.14 it holds the object’s fills and strokes too, read only, each stroke with its width, and from 0.15 its join, cap and miter limit. _context.item says whether the effect is on the object or on one of its paints. The objects beside it are still not given.
  • Filters are given each stroke’s join, cap and miter limit and each object’s effect records, and may return effect records (0.15). From 0.16 a filter keeps up to 1 MiB of data with the document (documentData).
  • Persistence: applying a live effect stores {"id": "plugin.<id>", "params": {…}} in the object’s appearance (Effect { id, params: serde_json::Value, visible }, crates/doc/src/appearance.rs). Documents keep the record when the plug-in is missing and draw the object unchanged.
  • Not in v1: tool plug-ins, panel plug-ins, host callbacks (progress, cancel), importers, live effects that change paint. File-format plug-ins came with the exporters (0.14).

Other facts that shape the design

  • No generic per-object metadata. Node has attrs: Option<Box<ObjectAttributes>> with only centre display, image map, URL and note (crates/doc/src/node.rs). The effect record is therefore the right place for embroidery parameters.
  • Document-level foreign data lives in Document.unknown (used for the perspective grid and brushes), preserved on round trips (crates/doc/src/lib.rs). From 0.16 the data filters keep with a document is there too, under pluginData.
  • SVG import keeps only the attributes it understands. The importer looks attributes up by name (presentation attributes, references, names such as inkscape:label) and has no place to keep unknown ones (crates/svg/src/import.rs), so an Ink/Stitch SVG opened in VectorCraft up to 0.16 loses its inkstitch:* parameters. From 0.17 VectorCraft keeps attributes in other applications’ namespaces from SVG import to SVG export, and reads none of them. SVG export can embed the whole native document (vectorcraft:document) when editing data is preserved.
  • Export formats are a static table (FORMATS in crates/engine/src/cmd/fileio/mod.rs). From 0.14 an exporter plug-in adds a format to it, plugin.<id>, which is how StitchCraft can add PES.

The tools an object filter was to give are VectorCraft’s own commands (tools) and M6.12’s 2 filters (Stroke to Satin and Test Sheet).

<ns> is a reverse-DNS namespace defined in one constant (PLUGIN_NAMESPACE) in the VectorCraft adapter, which reads the effect records too. The adapter makes the ids from it, a plug-in’s with plugin_id and its live effect’s with effect_id, and effect_name reads one back. The plug-in crate and the compatibility gate use the same functions. A live effect’s id ends with its stitch family’s (stitchcraft_params::Family::id). Manifests are generated from the parameter registry; a test validates each against VectorCraft’s manifest rules (id charset, ≤ 64 parameters, names, ranges, and from 0.14 the keys that say how the dialog shows a parameter), so a manifest VectorCraft would refuse fails the tests before a release.

Modules. The plug-in crate builds one module for each family, chosen by a Cargo feature named after the family: stroke, satin or fill, one for each machine format, by its extension: pes or dst, and one for each filter: settings, stroke-to-satin and testsheet. Without one it builds M0.6’s hello effect. The modules contain the same code, which the native tests run whichever it is, and the feature only picks the manifest and the run that vc_manifest and vc_run serve. cargo xtask compat contract builds the nine modules, notes their sizes and loads them into VectorCraft’s host.

Manifests. A family’s manifest is made from the registry when VectorCraft asks for it, so a parameter added to the registry shows in the dialog without another change. A key that several families declare, each its own way, is in each family’s manifest as that family declares it (parameter registry, rule 7). VectorCraft’s parameters are numbers, whole numbers, toggles and choices, and each always has a value. VectorCraft 0.14 adds texts and lists of numbers, which older releases refuse. A record stores every declared parameter, at its default when the user leaves it. So a parameter is declared when one such value means what the parameter means:

  • a length, an angle, a percentage or a number as a number in its range, and a count as a whole number;
  • a list or a pair whose default is one value as that value, which stands for the whole list or both sides, as in Ink/Stitch;
  • an optional length that 0 leaves unset as a number from 0.

Texts, seeds, and settings left empty to take another’s value keep their defaults. In the registry today they are the custom locks’ steps, random_seed, a fill underlay’s angles, a satin’s zigzag underlay insets and its shortest random split. A choice leaves out the options that a text spells out, which are the custom locks, and fill_method leaves out Ink/Stitch’s legacy fill, which StitchCraft sews as a tatami fill (REQ-FILL-005). satin_column belongs to the effect, which sets it from its family. The dialog opens with the group that declares the family’s method. The groups only the family uses, for its default method, come next, then those it shares with the other families, then those of its other methods, such as the zigzag stroke’s. The settings every element shares come last, as in Ink/Stitch’s dialogs.

How the dialog shows them (REQ-VC-012, M6.10). From 0.14 a parameter can say how the dialog shows it, and the plug-in says all of it from the registry (apps/stitchcraft-vc-plugin/src/dialog.rs):

  • Its row has the registry’s label, and the unit of its kind of value: mm, % or °.
  • The registry’s groups are the dialog’s sections, as they are the headings of the reference pages. VectorCraft draws a section where its group first appears, with every row of the group in it. Each group’s rows come together in the manifest, and a release before 0.14 shows them in the same order.
  • Its help is the registry’s help as plain text, cut at a sentence within VectorCraft’s 1,000 characters. A choice’s help ends with what each option means, by its label in the registry: VectorCraft’s drop-down list shows the ids that designs store, such as tatami_fill. Its help page is its entry in the parameter reference on the docs site, the book of main (dialog::SITE_URL). The docs check finds the page and the heading each manifest links to.
  • Each row shows only while the method is one the parameter applies to. Where the registry shows a setting only with some values of another, as its when says, the dialog does too: the length variation of a random stitch length shows while that is on, and a satin’s staggers for staggered splits. Rows that nothing in the dialog would show are left out. VectorCraft gives the plug-in the value of a hidden row as well, so what the dialog shows never changes what sews.
  • The plug-in’s own parameters, the preview level and the exporters’ 2 options, have a label, help and a page too.

A release before 0.14 ignores these keys, since its ParamSpec reads a parameter’s type, range and default and lets other keys pass (crates/plugins/src/manifest.rs at 0.12.0). Its dialog shows the keys and every parameter, as it did. The compatibility gate’s pictures of the dialogs are taken in the pinned release’s window, and the window probe checks that each shows the rows the manifest shows at the defaults, by label, each with the control of its kind.

What a live effect shows. A family’s effect sews its object with the engine’s generate, on the reference machine and with no neighbours, as one object of a design. It returns the stitches as geometry, the exact level below. When it can’t show stitches, it gives back why. VectorCraft then draws the object as it is and shows the message as the plug-in’s last error. That happens when the object cannot be sewn or sews no stitch, with the message that says why. A drawing that vanished instead could not be clicked to change the setting that emptied it. ABI v1 has no way to pass VectorCraft the warnings about stitches the effect shows, and stitch export reports them. How much of the stitches it shows, within what VectorCraft lets it spend, is its preview level (below).

The stroke an effect follows (REQ-VC-010, M6.8). A satin column drawn as one path and a zigzag stroke are as wide as their stroke. From 0.14 VectorCraft gives a live effect its object’s fills and strokes, and a stroke or a satin effect on the object follows the topmost stroke that has a paint and a width. It reads the stroke’s width, and from 0.15 its join, cap and miter limit, with the reader’s own code (stroke_style in crates/stitchcraft-vectorcraft). stitch export follows the topmost stroke VectorCraft draws, and the 2 can differ in 2 ways. VectorCraft gives a live effect every stroke of its object without its opacity or whether it shows, and gives it none of the paints of the groups around it. Given no stroke, before 0.14, for an object without one, or where only a group’s stroke paints it, the effect leaves a satin column drawn as one path and a zigzag stroke as they are, with SC-I0810. An effect on one of the object’s fills or strokes leaves the object as it is too, with SC-I0810: stitch export doesn’t use such an effect (SC-W0807).

The workflow

  1. Draw the art in VectorCraft as usual.
  2. Select an object → Effect › Plug-ins › StitchCraft Fill (or Stroke / Satin) → set parameters in the generated dialog. The parameters are now stored on the object (undoable, saved in the .vectorcraft file) and the object shows a stitch preview.
  3. Save the document.
  4. stitch export design.vectorcraft -o design.pes --preview design.png writes the machine file, for the machine --profile names, or else the one the document keeps (below), or else brother-pe800-5x7, and a picture of what will sew. It says what the reader left out or changed, with the engine’s warnings. stitch export is another name for stitch plan, which reads a VectorCraft document (.vectorcraft, .drawcraft, or a .vctemplate template) as it reads an SVG file (REQ-VC-008), and --report adds the JSON report. A bug-report bundle includes the part of the document the reader reads, which is its JSON without the images after it. Its replay reads that part the same way. From VectorCraft 0.14, File › Export › Export As writes the same file with StitchCraft’s exporters, without saving first (below).

Stitching order is paint order (bottom first). Hidden objects are skipped, as VectorCraft draws nothing for them, and locked objects are stitched. Thread colours come from the object’s fill for a fill, and from its stroke for a stroke or a satin column, as in Ink/Stitch, mapped to the profile’s palette.

Exporters: File › Export writes PES and DST

VectorCraft 0.14 added exporter plug-ins (the RFC’s P1). File › Export › Export As lists each after the built-in formats by its name, and document.export writes one for a path with the extension it lists. VectorCraft gives the exporter the document as a native .vectorcraft file’s JSON, as document.save writes it but without the data of images of 8 KiB or more, with the parameters of the dialog it shows when the file is picked, and the file’s extension and name. The exporter returns the file in base64, with warnings for the user, or declines with a message, and then nothing is written (VectorCraft’s docs/plugins.md, Exporters).

M6.9 makes StitchCraft’s formats exporters (REQ-VC-011, apps/stitchcraft-vc-plugin/src/export.rs). There are two, PES embroidery (StitchCraft) and DST embroidery (StitchCraft), each a module of its own, and a VectorCraft before 0.14 refuses to install them. An exporter writes the file stitch export writes of the document:

  • It reads the document with the same reader and plans it with the engine for the machine its profile option names, and the design takes the file’s name. The option’s default, document, is the machine the document keeps, or brother-pe800-5x7 when it keeps none, as stitch export plans it without --profile (below). Reading the file back, as stitch export does, stops it at a writer’s bug (SC-E0009). The budget is stitch export’s own too. Its auto option digitizes the objects without StitchCraft effects, as --auto does, and sews them in the order StitchCraft chooses. The exporters have no switch like --sort-colours, and the objects with effects keep their order among themselves (image to embroidery). Level B of the compatibility gate exports a document with VectorCraft’s command line and checks that the files are stitch export’s, byte for byte.
  • What stitch export says, the export says as its warnings, one line each, naming the object and with the hint after it. VectorCraft shows 100 of at most 500 characters each, so of more the last says how many more stitch export lists.
  • When anything said is an error, the exporter declines with the first, after how many there are, and VectorCraft doesn’t write the file, as stitch export doesn’t (REQ-CLI-003). VectorCraft shows the first 300 characters of a decline, after plug-in failed:.

An export may run 10 billion instructions, and 4,000 more for each byte of the document, and 300 seconds. The engine’s budget is stitch export’s, so a design that needs more is stopped by VectorCraft with its own error, plug-in exceeded its instruction budget, and stitch export writes it. The contract test req_vc_011_a_fill_of_the_whole_hoop_exports_within_vectorcraft_s_limits measures the largest designs the reference machine sews (VectorCraft 0.16.0 to 0.18.0 alike, 2026-10-29):

Design, each fill with its defaultsInstructionsOf those allowed
A fill of 128 × 178 mm, the 5 × 7 in hoop’s whole field1.6 billion16 %
63 fills of 14 mm squares across the field4.3 billion43 %

A fill’s work grows less than its area, and every fill takes some whatever its size: the squares cover half the field and take more than twice as much. About 140 fills of that size are as many as an export can plan, which few designs for a home machine’s hoop reach, and stitch export writes the others. The test sheets drawn as designs export within 17 % of what an export may run, once the Test Sheet filter has drawn them into a document (below). A live effect is given no warnings channel, and an exporter no picture: stitch export --preview still draws what will sew.

Design settings and machine kept with the document

Ink/Stitch keeps 3 settings for the whole design with an SVG file, collapse_len_mm, min_stitch_len_mm and min_satin_stroke_width_mm (SVG input), and a VectorCraft document has no place of its own for them. VectorCraft 0.16 keeps up to 1 MiB of JSON with a document for each filter, the RFC’s P5. The filter returns it as documentData, and the native file saves it in document.unknown.pluginData under the plug-in’s id. An exporter reads every plug-in’s in the document it is given, and a live effect isn’t given it.

M6.11 makes a filter keep them (REQ-VC-013): StitchCraft Design Settings, in Object › Plug-ins (<ns>.settings, apps/stitchcraft-vc-plugin/src/settings.rs). Its dialog has the machine, a choice of the built-in profiles, then each design setting as a length. The settings’ names, labels and help come from stitchcraft_engine::design::SETTINGS, the table the SVG adapter reads Ink/Stitch’s settings with. The machine is StitchCraft’s own, as Ink/Stitch’s hoop is the page. On OK the filter keeps all 4, the settings under Ink/Stitch’s names and the machine’s id as profile:

{"profile": "brother-pe800-5x7", "collapse_len_mm": 3, "min_stitch_len_mm": 0, "min_satin_stroke_width_mm": 1}

The filter returns each object it is given by its id alone, as VectorCraft deletes an input object that a filter leaves out, and so its run leaves every object as it was.

The VectorCraft adapter reads the data (stitchcraft_vectorcraft::settings) as the SVG adapter reads Ink/Stitch’s. The settings kept become the design’s settings, and the machine kept is VectorCraft::machine, which stitchcraft_vectorcraft::machine reads before the rest of the document. SC-W0812 names what doesn’t read, which keeps its default:

  • a setting that isn’t a length of 0 or more, or that this StitchCraft doesn’t know;
  • a machine it doesn’t have;
  • data that isn’t an object, whose settings all keep their defaults.

In a damaged file whose pluginData isn’t an object, VectorCraft finds nothing kept, and so does the adapter. stitch export and stitch bug-report plan for the machine --profile names, or else the one kept, or else the reference machine (stitchcraft_cli::commands::plan::machine_for). The exporters’ profile option starts at document, which follows the same order, and names a built-in profile only when the user picks one.

VectorCraft opens a filter’s dialog at its manifest’s defaults, not at what the filter kept. The filter keeps every setting each time it runs, and the user sets all of them again. A live effect isn’t given what the document keeps, and the previews are planned with the default settings for the reference machine. A longer shortest stitch kept with the document shows in the machine file and in stitch export --preview, and not in the preview.

The contract test req_vc_013_the_settings_filter_keeps_the_machine_each_exporter_plans_for has VectorCraft’s host run the filter as plugin.run runs it, then exports the document with what it kept. Level B’s settings scenario does the same with VectorCraft’s command line: a shortest stitch of 1.5 mm changes the PES file, the exports are stitch export’s, and with the small hoop kept the export of a 1 in square fails with SC-E0701.

Tools: VectorCraft’s own commands

The plan had one object filter, <ns>.tools, to make a satin column from 2 paths, add a rung, bake a preview to paths, make a line into a satin column and draw a test sheet. VectorCraft’s own commands do the first three, and M6.4 checked them in its source, 0.7.0 to 0.12.0. Make Compound Path changed at 0.10.0. Before, the compound path takes the appearance of the frontmost path it is made of and turns none round. From 0.10.0, it takes the backmost path’s, and reverses each path in front that winds the same way as the backmost one. A straight path counts as winding clockwise, so of 2 straight rails the front one is always reversed. So the StitchCraft effect is applied after the paths are joined, which works in every version:

TaskIn VectorCraftWhy it sews
Satin column of 2 pathsObject › Compound Path › Make (object.compoundPath.make), then the satin effectThe column turns a second rail that runs the other way back (reverse_rails, automatic), as Ink/Stitch does (REQ-VC-007). The reversal also starts a ring at what was its last node, and of 2 rings the second starts at its node nearest the first’s start (REQ-SAT-019)
RungPen tool line across the rails, then Make Compound Path with the columnWhich way the rung runs, and where among the paths it lies, doesn’t change the points it pairs. Before 0.10.0 the compound takes the rung’s appearance, and the effect is applied again
Baked previewObject › Expand Appearance (effect.expandAppearance)It runs the live effect and makes objects of what each fill and stroke paints, strokes outlined. Those are the preview’s shapes, which sew differently from the effect. Bake a copy to show, and sew the original
PresetsGraphic Styles (graphicStyle.new, graphicStyle.apply)Applying a style copies its effects into each object, or into the group it is applied to, whose effects apply to each path inside (REQ-VC-006)

The last two needed what ABI v1 gave a filter later, and M6.12 made them filters of their own.

Tools: Stroke to Satin and Test Sheet

M6.12’s 2 filters draw objects with StitchCraft’s effects, which a filter’s output may hold from VectorCraft 0.15 (the RFC’s P8). The VectorCraft adapter reads what a filter is given and writes what it gives back (stitchcraft_vectorcraft::filter). A paint, an effect record and an opacity given back are written as the JSON text VectorCraft gave, since VectorCraft keeps a paint’s swatch, and a record as it was, only when they come back unchanged, which it tells by their values. A path is written in points, each coordinate the shortest decimal that reads back to it. VectorCraft admits a new effect record as effect.apply would apply it: a StitchCraft effect’s only while its plug-in is installed, its parameters filled in to their defaults.

Stroke to Satin (REQ-VC-014, apps/stitchcraft-vc-plugin/src/stroke_to_satin.rs), Ink/Stitch’s Stroke to Satin, once Convert Line to Satin, makes each subpath of each selected path that has a stroke into a satin column drawn with its rails and rungs. The line is the column’s centre line, as wide as the stroke a satin effect on it would follow, with that stroke’s join. The engine makes the rails and rungs it makes of such a column when it sews one (REQ-SAT-016, REQ-SAT-017), and draws them as straight lines, each rung longer than the gap between the points it pairs by a hundredth of it at either end, so that it crosses the rails (satin generators). Read back, the column pairs the same points, so it sews as the line did. A column of 2 rungs or none gets a rung at its start too, since Ink/Stitch’s rule would read the 2 longest lines as its rails (DEV-SAT-007).

Each column is a compound path without fills. Its stroke is the line’s paint one CSS pixel wide, which shows the rails and draws the satin effect’s stitches thin. The first column takes the object’s place, and the others go above it with its opacity. The satin effect takes the place of the object’s first StitchCraft effect, with the line’s satin settings or the defaults. The object’s other StitchCraft effects are left out, and its other effects kept. An object the satin effect already reads as rails is given back as it is. The filter refuses with SC-E0814, and the document stays as it was, when the selection is empty, a path has no stroke that paints or can’t be used, or a line can’t be made into a column that sews as it does. Such a line’s rails can’t be made whole (SC-E0214, SC-W0213), or they cross each other. Before 0.15, which drops the records a filter gives, it declines with SC-E0813.

M6.4 measured making the rails inside VectorCraft’s host at up to 162 million instructions, where a light run gets about 52 million. The rails are the line offset as GEOS offsets it, which builds the boundary of the whole stroke for each rail. So Stroke to Satin is a heavy filter (P4): VectorCraft 0.17 gives each run 1 G instructions and 300 s, once the user allows it at install, and runs it in the background. The contract test req_vc_014_stroke_to_satin_makes_columns_that_export_as_the_lines_did converts M6.4’s lines in VectorCraft 0.17.0’s and 0.18.0’s hosts alike, 3 mm wide, as plugin.run runs a filter, and StitchCraft’s PES exporter writes each column’s file as it wrote the line’s (2026-10-29):

That is at most 360 instructions for each unit of the engine’s work, which the plug-in prices at 450, and the filter stops with SC-E0004 before VectorCraft would. A VectorCraft before 0.17 runs it as a light filter, which almost every curved line outruns, and stops it with its own error.

Test Sheet (REQ-VC-015, apps/stitchcraft-vc-plugin/src/testsheet.rs) draws one of the sheets drawn as designs, TS-02B to TS-09, into the document: the sheet’s design moved by whole millimetres so that its middle is nearest the middle of the artboard _context names (Design::moved). Each element is an object named by its id, with its path and its thread as the paint its family sews with. Its settings are its family’s effect record, each the value its dialog row takes, which reads back as the setting it was. The objects selected are given back as they are, and the sheet goes above them. The document sews as the sheet’s design moved. A fill’s rows lie where the design’s origin puts them, so moved they may fall elsewhere across a shape, and the sheet looks the same. The threads lose their names in the Brother palette, since VectorCraft unlinks the swatch of a paint a filter gives, and the PES file is the same. VectorCraft 0.15 keeps the records, but with an empty selection it looks to a filter as 0.14 does, which would drop them. Only the documentData every filter gets from 0.16 tells them apart, so before 0.16 the filter declines with SC-E0813. The sheets drawn stitch by stitch are plans, which no object holds.

The contract test req_vc_015_each_test_sheet_draws_into_a_document_that_exports_within_vectorcraft_s_limits draws each sheet into a new document in VectorCraft 0.17.0’s and 0.18.0’s hosts alike, and exports it with the PES exporter (2026-10-29). Drawing takes 14 to 25 million instructions, at most half of a light filter’s run. Exporting takes 23 million to 1.6 billion, at most 17 % of an export’s, the most for the fills of TS-07, TS-08 and TS-09.

A live effect gets 50 million instructions, plus 4,000 for each byte of its input, and 5 seconds. Spike M0.6 measured what JSON costs in VectorCraft’s host (wasmi 2.0, in VectorCraft 0.12.0 and on main at 8bc6532, 2026-10-17). The hello plug-in reads its input with serde_json and writes the geometry back:

The plug-in turns the instructions it has left after reading its input into a budget of the engine’s work units, and prices what it writes by the anchor. The preview_level parameter, auto by default, lets the user pick a level (VectorCraft reserves the name preview). A level the user picks gets the whole budget, and when that is not enough, SC-I0810 names a cheaper one. The units of a stroke’s work and of a satin column’s cost the same on every shape measured, so a budget of units bounds their exact previews. A fill’s units vary too much for that. A 7 mm square’s exact preview already takes more than half of what VectorCraft allows, and a budget of units that ran out early, in the dearer work, took 71 million instructions. So auto shows a fill’s rows, and its exact preview is the user’s to pick, with all that VectorCraft allows, which stops one that needs more with its own error. A satin column drawn as one path makes its rails from its centre line first, in many units of about 330 instructions each, which the satin column’s price counts as dear as its stitches. One bend takes 33,100 units, so auto shows the outline of a centre line that bends. Its exact preview is the user’s to pick too: 12.6 million instructions for one bend, 25 million for a quarter circle of 17 points and 46 million for a sine curve of 32 points, of the 51 to 55 million VectorCraft allows them. The contract test req_vc_003_every_preview_level_finishes_within_vectorcraft_s_limits runs each level on shapes of growing size on every track the compatibility gate tests, and fails when VectorCraft stops a run that must finish. It prints what each run takes, which the budget’s numbers are measured from. hello_reads_and_writes_json_within_the_recorded_budget still measures what JSON costs. The real stitches are always available from the CLI preview, and the RFC’s overlay channel (P3, in review upstream) would remove this limitation.

Paint caveat: a live effect changes only geometry. A fill preview’s ribbons are painted with the object’s own fill, and a stroke preview with its stroke. From 0.14 a stroke or a satin effect reads its stroke’s style, and still cannot change the paints. Users set the fill/stroke to the thread colour, which they want anyway for export.

Commands in v1

Ink/Stitch’s commands are symbols linked to an object, and ABI v1 has nothing to link. trim_after and stop_after are ordinary parameters. StitchCraft reads the others from names, an object’s or a layer’s, which VectorCraft’s Layers panel sets (REQ-VC-009). A name is read when it begins with stitch:, after any white space, in any mix of upper and lower case. Its word ends at the first white space, so a note can follow it:

NameInk/Stitch’s commandWhat StitchCraft does
stitch:ignoreignore_object, ignore_layerLeaves the object or the layer out with everything in it, and lists it with SC-I0811
stitch:start, stitch:endstarting_point, ending_pointMarks where the fill or the satin column grouped with it starts or ends, and never stitches the marker. Until the generators start and end at hints (REQ-GEN-001, M8), they choose where, and SC-W0807 names the marker. A group or a layer is never a marker: SC-W0807 names it, and what it holds is read as under any other name
Any other word after stitch:Ignores the name, and SC-W0807 names the object, in case the word is a misspelt marker

Hiding an object leaves it out too, without a word, and a name on a hidden object says nothing. A live effect is given its object’s geometry, with its fills and strokes from VectorCraft 0.14 (VectorCraft’s docs/plugins.md, Input), never its name. So VectorCraft’s preview still shows the stitches of an object these names leave out, a marker included, when it has a StitchCraft effect or is in a group that has one. stitch export leaves them out. The RFC’s sixth proposal, still open in that part, would let a live effect read the markers beside its object, so its preview could start and end at them.

Reading .vectorcraft files (stitchcraft-vectorcraft)

stitchcraft_vectorcraft::read turns a .vectorcraft file into a design, and reports what it left out or simplified, as the SVG adapter does for SVG files. It reads the format as VectorCraft documents it (crates/format and the types crates/doc saves) and links none of VectorCraft’s crates. VectorCraft versions 0.7.0 to 0.12.0 were read for this design.

The container. A file is JSON, compressed with gzip when its first two bytes are 1F 8B. VectorCraft compresses from format 3 on, but the adapter reads any version either way. In format 4, images and other large data can follow the JSON, behind the marker \n\0VCBLOBS\0. JSON text never holds a NUL byte. The JSON ends at the first one, and nothing after the marker is read. The top level must say "format": "vectorcraft", or "drawcraft", VectorCraft’s earlier name, and hold a document. Formats 1 to 4 read alike: points as {"x", "y"} or [x, y] in any of them. A newer format is read as far as it goes, with SC-W0803, where VectorCraft’s own readers refuse it.

Limits. At most 64 MiB of JSON, unpacked, as for an SVG file, and the command line reads at most 64 MiB of any file (REQ-CLI-005), images included. A gzip stream is unpacked only up to the marker, and no further than the limit. Nesting deeper than the JSON reader allows (128 levels, about 40 levels of groups) refuses the file. VectorCraft itself keeps 32. The JSON is read into the few things the adapter uses, and the rest is skipped as it is read: images, previews and text runs are never kept. Every object, appearance item, effect and anchor charges the budget, and so does each element for its copy of the object’s path.

Coordinates. VectorCraft keeps every path in document coordinates. Moving or scaling a group moves its paths’ anchors, so layers, groups and compound paths have no transform. Coordinates are points, 1/72 inch, with y down, and the adapter multiplies them by 25.4/72 into millimetres. The document’s origin stays the origin. Coordinates are read exactly, as VectorCraft reads them, from their text in the JSON. An anchor’s handles are absolute positions. A missing handle, or one within a billionth of a point of its anchor, leaves that end of the segment straight, and a segment without handles is a line.

What is stitched. The layers in order, bottom first, and in each its children in paint order:

  • Paths and compound paths are the art. A compound path’s children are one shape, with the compound’s appearance and fill rule.
  • Groups and layers pass their children on, and their StitchCraft effects with them (below). Clipping is left for M8, as in the SVG adapter: a clipping group’s or layer’s art is stitched whole, with SC-W0807.
  • Hidden objects, and everything in them, are left out without a word, as VectorCraft draws nothing for them. So are objects and paints of opacity 0, paints turned off and strokes of width 0.
  • Objects and layers named stitch:ignore, and everything in them, are left out with SC-I0811. Start and end markers are never stitched (commands).
  • Template layers, layers that don’t print, and guides are left out with SC-I0809. VectorCraft shows them, dimmed or as guides, but prints and exports none of them.
  • A Shaper group’s sources are left out. The group shows the shapes it makes of them, and keeps them as its first child, transparent. The Layers panel’s Make Clipping Mask (layer.clippingMask.toggle) puts a Shaper group’s clipping object before them.
  • Text, images and symbols, and the objects VectorCraft computes as it draws them (blends, envelopes, meshes, repeats, placed documents and VectorCraft’s Intertwine objects), are left out with SC-W0807. The message names VectorCraft’s command that makes paths of them, such as Type › Create Outlines for text. So is a kind of object this version doesn’t read.

Paints and threads. An object without StitchCraft’s effects is stitched as Ink/Stitch stitches an SVG shape. Its visible fills are filled, in the appearance’s order, and its visible strokes then have a running stitch each. Since M13.1, read with --auto (stitchcraft_vectorcraft::read_with), the elements of an object are automatic instead when neither it nor a group or layer around it has a StitchCraft effect (image to embroidery, REQ-AUTO-001). StitchCraft then chooses their stitches by their width. Read with --sort-colours, the objects with effects sew in the order StitchCraft chooses too (REQ-AUTO-011). A stroke’s cap is read with its width and join, and an automatic line’s stitches follow its round or square caps. Of a line sewn across its width, the reader names the alignment inside or outside a closed path and the width profile, which its stitches don’t follow (SC-W0807, REQ-AUTO-005). The thread’s colour is a solid paint’s colour, with CMYK and grey converted by VectorCraft’s formula without colour management ((1 − c)(1 − k) and 1 − k) and Lab through sRGB. A gradient gives its first stop’s colour, with SC-W0807 unless every stop has that colour, and a pattern gives black, with SC-W0807. A stroke’s width, in points, and its join, with its miter limit (10 when the file omits it, as VectorCraft draws it), shape a satin column drawn as one path. A stroke drawn with a brush is stitched along its path, without the brush’s art, with SC-W0807.

What VectorCraft draws of a stroke that its stitches don’t follow is named with SC-W0807, and the message says how to stitch it, usually with Object › Path › Outline Stroke:

  • A stroke’s arrowheads are not stitched, and a dashed stroke is stitched along all of its path. A dash pattern that VectorCraft draws solid, with a length below 0 or that is not a number, or only 0s, is no dash.
  • A stroke painted below a fill is sewn after the fill, over it.
  • A satin column or a zigzag made of a stroke is as wide as the stroke all along and centred on the path. VectorCraft draws a closed path’s stroke inside or outside it when it is aligned so, and varies its width along a width profile. It also caps an open path’s ends with round or square caps. A running stitch along the path is the same whichever way the stroke is drawn.

A group’s or a layer’s own fills and strokes, which paint every member, are not stitched as shapes of their own. They give StitchCraft effects their thread and stroke (below), with SC-W0807.

Effects. StitchCraft’s live effects are kept in the object’s appearance as {"id": "plugin.dev.stitchcraft.<family>", "params": {…}, "visible": true}. The family is stroke, satin or fill (stitchcraft_params::Family). An object with visible StitchCraft effects is stitched as they say, in their order, instead of by its paints. A fill effect fills the object’s shape, a stroke effect stitches along it and a satin effect makes a satin column of it. With this rule, an object sews what its effects say and nothing else. Each effect is sewn on the shape as it is drawn. VectorCraft draws an effect after the first on the stitches of the one before, though, so the preview of an object with 2 is not what is sewn, and SC-W0807 says so, once for an object and once for a group. A fill with an outline takes 2 objects: the shape with a fill effect, and a copy pasted in front of it (Edit › Paste in Front) with a stroke effect. The record’s parameters are the element’s. A number is written as a decimal, a toggle as true or false, a choice as its id and a list as its values with spaces between. What the record leaves out takes its default, as in the plug-in’s dialog. The thread is the colour of the topmost fill VectorCraft draws for a fill, and of the topmost stroke for the others, falling back on the other kind. An opaque paint comes before one of opacity under 1, which lets what is under it show. A stroke or satin effect follows the width and join of that stroke, or a width of 0 when none is drawn. VectorCraft writes a stroke of paint none for an object without one, which it doesn’t draw. A satin column too narrow to stitch across is sewn as a stroke, with SC-W0212. SC-W0807 names a zigzag 0 mm wide. VectorCraft’s own effects change what an object draws, and are left out with SC-W0807 (Object › Expand Appearance makes paths of what they draw).

A group’s effects (REQ-VC-006). VectorCraft runs a group’s or a layer’s geometry effects on each path and compound path inside it, however deep, with the group’s bounds as their frame (reshape_leaves in crates/effects, 0.7.0 to 0.12.0), and paints what they return with the path’s own paints. The group’s own paints paint the shapes inside it as its effects and those of the groups around reshaped them (evaluate_container). They go over its contents. The Contents row of its Appearance panel (contents_index) is last in the list by default, and the paints listed under it go under the contents. StitchCraft’s live effects are geometry effects, and applying a graphic style to a group puts its effects and paints on the group. So each path inside sews as the group’s StitchCraft effects say, and as the preview shows it. A name can leave one out (commands). Its thread and stroke come from the paints over it, the topmost first, as for an object’s own paints. The groups’ paints over their contents come first, the outermost first, then the object’s own, then the groups’ paints under their contents, the innermost first. The same order applies to an object’s own effects, which VectorCraft paints with its own paints, under the groups’ paints over the object’s shape. A path that neither its own paints nor a group’s paint is invisible, and is left out without a word.

A clip group’s first object is its clipping object. VectorCraft paints a path, a compound path or text there with its own paints alone (clip_paint in crates/doc): its fills under the clipped art and its strokes over it. A group’s effects run on such a path too. After Make Clipping Mask it has no paint, and sews nothing. VectorCraft draws nothing of a group or an image there, which an imported file can have, and neither is sewn. Where StitchCraft effects meet from more than one level, a path’s own and a group’s, or 2 groups’, VectorCraft draws one effect run on the stitches another drew, which a machine cannot sew. The path sews as the nearest effects say, and SC-W0807 names it.

Ids. An element is vc:<object id>:<what>: fill or stroke for a paint, with its rank among the object’s fills or strokes from the second on (fill.2), and the family for an effect. VectorCraft keeps an object’s id when it saves, so a report and a preview name the same object. A repeated id gets ~2, ~3, … as in the SVG adapter.

Reports. SC-E0806 refuses a file that isn’t a VectorCraft document, or is larger than the adapter reads. SC-W0807 names what isn’t stitched. SC-W0808 names geometry that can’t be used, such as a number that doesn’t read or a point more than 10 m from the origin, and a shape that draws nothing. SC-I0809 lists the layers and guides left out because VectorCraft doesn’t print them, and SC-I0811 the objects and layers left out by their names. The compatibility gate will have each VectorCraft version it tests write files for the adapter to read back (Level B, M6.6).

Importing Ink/Stitch SVGs into VectorCraft

Because VectorCraft up to 0.16 drops inkstitch:* attributes on SVG import, phase 1 offers stitch import-inkstitch design.svg -o design.vectorcraft: our SVG adapter reads the Ink/Stitch file and writes a VectorCraft document with the same art and the parameters as live-effect records (M8). From 0.17 VectorCraft keeps the attributes from SVG import to SVG export, but its live effects read none of them.

6. Phase 3: an in-tree crate (optional)

If ArtCraft wants embroidery natively — or in a fork — a vectorcraft-embroidery crate at VectorCraft’s L2 (depending on geom, doc and our MIT/Apache engine crates) would provide commands in crates/engine/src/cmd/embroidery.rs (apply settings, export PES/DST through the FORMATS table, test sheets), panels in crates/ui-egui (Embroidery parameters, Stitch Simulator) and a satin rung tool in crates/tools.
