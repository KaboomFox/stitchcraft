StitchCraft

Engine pipeline

From a Design to a checked StitchPlan. Each stage is a module in stitchcraft-engine with its own tests; stages communicate only through the types in the data model.

Design ──▶ 0 auto ──▶ 1 normalize ──▶ 2 validate ──▶ 3 generate (per element) ──▶ 4 assemble ──▶ 5 finalize ──▶ 6 check ──▶ StitchPlan
              │            │               │                 │                         │              │              │
              └────────────┴───────────────┴───── diagnostics accumulate at every stage ┴──────────────┴──────────────┘

0. Automatic digitizing

Since M13.1, before anything else, each element the host marked automatic, a shape without settings read with --auto, becomes the ordinary elements its width calls for, with the settings that say so (stitchcraft_engine::auto::digitized, image to embroidery).

  • An area is sewn as it is, apart from its narrow parts: each becomes a running stitch along its centre line (M13.4), or, no wider than a satin column, satin columns along its centre lines (M13.5), and the rest of the area the fill of its other parts.
  • A line that runs is sewn as it is, tripled from 0.5 mm wide.
  • A line sewn as a satin column becomes a column for each of its subpaths, or the fill of a subpath a column cannot follow (SC-I0902).
  • A wider line becomes the fill of the area it paints.

Every stage after it sees only ordinary elements. A digitized shape sews, offers its neighbours what it offers and is said of as the same shape set by hand would be. SC-I0901 counts the shapes digitized. A design without automatic elements passes through unchanged and uncopied. Each automatic element has the budget’s work to itself, naming its parts included, and one that needs more is left out with SC-E0004 (REQ-GEN-002). Digitizing doesn’t add an error of its own (REQ-AUTO-006). What cannot be sewn as its width says is sewn otherwise or left out with a warning.

The digitized elements are then sewn as neighbours, in an order of their own. What overlaps keeps its paint order, and a line sews after the fill it borders. Then each thread sews as long as it can, the nearest element next (image to embroidery, SC-I0907). Elements with settings keep their order among themselves, unless --sort-colours is given. The switch brings a design without automatic elements through this stage too. An element sewn in several threads moves as one, its colours together and in their order (REQ-AUTO-024).

1. Normalize

Per element, independent of the others:

  • Flatten curves with the element’s tolerance (a tenth of running_stitch_tolerance_mm for strokes, and a tenth of a CSS pixel for fills and satin columns, as Ink/Stitch flattens them). Curves are halved (de Casteljau) until each piece’s control points lie within the tolerance of its chord (stitchcraft_engine::normalize::stroke), using only arithmetic and square roots so that every platform gets the same points. kurbo’s adaptive flattening is not used for this: in 0.13 it calls powf (CubicBez::to_quads) and hypot (QuadBez::estimate_subdiv) from the platform’s maths library, whose last bits differ between systems (determinism). Corners, joins between segments that turn by more than 30°, are marked so running stitches land exactly on them; a curve’s own bend is never a corner.
  • Regions: a fill’s subpaths are cut wherever they meet, and its fill rule says which faces between them are filled. The edges between filled and empty faces become outlines and holes, each turned one way, and parts too small to sew are left out with SC-W0303 (fills › Region, stitchcraft_engine::normalize::region).
  • Satins: classify subpaths into rails and rungs (satin), or make them from a column’s centre line (single-path satin).
  • Strokes: each subpath becomes its own path piece, in document order.
  • Commands become hints (start/end/target points) on the element.
  • Clips: an element’s clips cut it, each the areas of its shapes together by their rules (REQ-GEN-005). A fill’s region is cut when it is built (region::build_clipped), before its underlay, expand_mm and its method see it. For a stroke, the subpaths are cut at their crossings with a clip’s outline (region::cut), as in Ink/Stitch. A manual stitch’s run from node to node, and other strokes’ are flattened as a shape’s outline is. Left whole, a subpath keeps its curves and sews as drawn, and each piece of a cut one sews on its own. Satin columns are sewn whole (SC-W0217), and an element wholly outside its clips isn’t sewn (SC-W0013). Automatic digitizing cuts its shapes first, so that what shows of them is digitized (auto::clips).

Adapters have already applied transforms and converted units, so normalization never sees host types.

2. Validate

  • Parameters are read by the registry as the element’s stitch type reads them. Blank text takes the default, and a setting the stitch type does not use, or that its other settings hide, is kept unread (parameters). A value that only the node’s other stitch type can read, such as a zigzag stroke’s 2 spacings under a meander fill, is left to it: the element takes the default, and SC-I0106 says so (REQ-PRM-006). The rest are checked for type and range, and the generator receives a typed struct or nothing.
  • Shapes are checked against the stitch type. A satin needs a subpath longer than a point (SC-E0201), a fill needs a non-empty region, and a running stitch needs a path longer than the minimum stitch length.
  • An element with an error diagnostic is skipped; the rest of the design still plans. A design whose every element was skipped yields SC-E0010. stitch plan writes the machine file only when no error is said, as Ink/Stitch writes its file only when no element fails (REQ-CLI-003).

3. Generate

Each element becomes stitch groups (stitchcraft_engine::generate): the needle points of each part of it that a jump may separate from the next, in sewing order. A stroke gives one group per subpath, and a part too small for a stitch gives none (SC-W0401). The element’s own settings stay with the element, and assembly reads them there: its thread, locks, trim and stop. A generator may give each group a thread of its own as well, which a tartan or a gradient fill needs (below).

The stitch type picks the generator. A stroke whose satin_column setting is on is a satin column, whatever its stroke_method says, as in Ink/Stitch. Its rails and rungs are recognized, what recognition finds is reported, and its satin_method picks the generator: the satin stitch, sewn from M4.2, the E-stitch, from M7.3, the S-stitch, from M7.4, and the zigzag satin, from M7.5. A satin column also reads the running stitch’s length (running_stitch_length_mm): the stitches that join its underlays are no longer than the first value. For any other stroke the generator is its stroke_method. running_stitch (the default) and manual_stitch are sewn from M3, and zigzag_stitch from M7.2, as wide as the stroke. A satin column drawn as one path no wider than the design’s min_satin_stroke_width is sewn as a stroke, with SC-W0212, as in Ink/Stitch (REQ-SAT-015). Wider, it is sewn between rails made from its line from M4.9 (REQ-SAT-016). A fill whose fill setting is off sews nothing, and nothing is said of it (REQ-FILL-003). Another fill’s region is built first, so what it leaves out and how it will be sewn are said (SC-W0303, SC-W0304, SC-I0306, SC-W0307) whatever comes next, and its fill_method picks the generator: the tatami fill, sewn from M5.4, which reads the running stitch’s length and tolerance for its travel between rows (the first of the lengths, as a satin column does), under the rows from M5.5, and sews its underlay before its top rows from M5.6. A fill set to Ink/Stitch’s legacy fill is sewn as a tatami fill without underlay, with SC-W0314: StitchCraft does not build that method (REQ-FILL-005). Nor does it take pull compensation, random stitch lengths or gap-filling rows, which Ink/Stitch’s legacy fill has no use for. A contour fill, sewn from M7.7, lays its rings with the tatami fill’s row spacing and sews them as one running stitch after the tatami fill’s underlay, reading the running stitch’s tolerance and random lengths for its path (fills). A meander fill, sewn from M7.8, lays a tile over each part and sews one path through it after the same underlay (fills). A circular fill, sewn from M7.9, sews a spiral round the middle of each part after that underlay too, and routes the spiral’s pieces as a tatami fill routes its rows (fills). A cross stitch fill, sewn from M10.1, sews a cross in each cell of a grid that each part covers enough of, with no underlay, the crosses that meet in one run. From M10.2 it sews each of Ink/Stitch’s 12 methods, its half crosses in rows routed as a tatami fill’s (cross stitch). The other stroke, satin and fill methods are skipped with SC-W0011 until their milestones. An element whose parameters are wrong (SC-E0101) is skipped too, and the rest of the design still plans.

Each element is generated with the shortest stitch for it: the larger of the machine’s (the profile’s min_stitch) and the element’s min_stitch_length_mm, or the design’s shortest stitch when the element sets none. A satin column is given its longest stitch as well, the element’s max_stitch_length_mm, which its split stitches keep to. A length shorter than twice the shortest stitch, a running stitch’s or a fill’s longest, is raised to it with SC-W0402: shorter, the plan would merge its stitches.

A preview that cannot afford a fill’s stitches shows its top rows (stitchcraft_engine::generate::rows, from M6.3). The fill’s settings are read as for sewing it, and what they say is said the same, but only the region is built and the rows laid over it: no needle point is placed and no route is searched. A contour fill has no rows, and shows its path round its rings, from M7.7. A meander fill shows its path through its tile as the element’s seed lays it, from M7.8, a circular fill the pieces of its spiral, from M7.9, and a cross stitch fill the bars of each of its crosses, from M10.1, or each half cross’s diagonal, from M10.2.

Rules every generator follows:

  • Pure: output depends only on (normalized shape, typed params, neighbours, seed, budget).
  • The needle before, the next element after. Elements are generated in sewing order (ADR 0014, REQ-GEN-003). Each is given the last needle point of the elements before it, whatever their thread, and what the next element offers to end near. That is its first point, or, when it starts at its own nearest point, its shape: a satin column’s rails or a tatami fill’s area. The offer comes from the next element’s shape and settings and the design’s, never its stitches, so nothing waits for a later element. A satin column and a tatami fill start and end by them (satin, fills). An element’s start and end positions, which its design places, take their place for the stitch types that use them, and a fill or a satin column with a start position offers it (REQ-GEN-001). Each ends near its next stitch, its point nearest the offer as Ink/Stitch’s geometry library finds it, a point of one shape inside the other’s area first (generators::next). From M10.15 an element in a run of underlays first is generated as 2 layers, and each layer gets its neighbours as an element does (underlays first).
  • Seeded randomness: each element’s generator is seeded from its random_seed, one of the settings every stitch type shares. When that is empty, a hash of its id seeds it. A seed replaces the id, as in Ink/Stitch. The PRNG is SplitMix64 from stitchcraft-core (determinism).
  • Budgeted: every inner loop charges work units. Each element has the budget’s work to itself. One that runs out (SC-E0004) is skipped, and the others still plan. The stitch limit is for the whole design. Assembly and finalize share the budget’s work once more, and running out there plans nothing. SC-E0004 then says so for the whole design. A generator also spends the design’s stitches on the needle points it makes (budgets, REQ-GEN-004). Each element gets what the elements before it left, and the first that needs more ends planning, with SC-E0004 naming it.
  • Roles: every stitch is tagged by its role. Assembly tags the stitches of groups as top and the lock stitches as lock. The jumps between groups are travel. Previews draw the lock stitches apart. A generator hands assembly its needle points without roles, so an element’s underlay, and the running stitches between its rows, are tagged top as well, until generators tag their own. From M10.15 the stitches of a run’s underlays are tagged underlay (underlays first).

Generators are listed in algorithms.

4. Plan assembly

Groups are joined into colour blocks in the order the elements sew (host paint order, bottom first, or the order stage 0 chose), by stitchcraft_engine::assemble.

Ordering

  • Assembly keeps the order the elements come in, so that embroidery stacking follows the art’s stacking. That is paint order, unless stage 0 put the automatic elements, or with --sort-colours every element, in an order chosen for few thread changes, in which a shape still sews after every shape it is drawn over, where they overlap by more than rounding leaves. No stage routes elements a host read. M10’s routing tools write their route into the document, whose paint order is then the route’s (routing tools). The elements of a run of underlays first keep this order too, with their underlays moved ahead of their top stitches (below).
  • A thread change starts a new colour block (REQ-ASM-001). Threads are compared by colour, as Ink/Stitch compares them: two names for one colour are one thread, and the block keeps the first. The thread changes inside an element too, where its groups’ threads change (REQ-ASM-006).

Underlays first

From M10.15, consecutive elements that set underlays_first sew all their underlays before any of their top stitches (ADR-0018). The setting is a toggle that every stitch type shares, off by default, and StitchCraft’s own. Ink/Stitch has no such order.

  • Runs. The engine finds the runs before stage 3, in the order stage 0 gives. A run is a stretch of consecutive elements that set the toggle and have one thread, compared by colour as above. It ends after an element with trim_after or stop_after. An element sewn in several threads (M10.5), or skipped for settings that don’t read, is in no run. An element that would make a run of one sews as it does without the setting, and a note says why its setting joins nothing.
  • 2 passes. A run sews its elements’ underlays in their order, then their top stitches in the same order. An element without underlay, such as a running stitch or a fill with fill_underlay off, sews in the second pass alone. The run’s last element keeps its trim or stop after its top stitches.
  • Layers. Each element of a run is generated as 2 layers, its underlay and its top, each in its place in the passes. A layer starts near the last needle point sewn before it and ends near what the next layer offers, which is what that layer’s element offers (stage 3). The element’s start position places the start of its first layer, and its end position the end of its top. Its settings are read and its shape built once, and the 2 layers share its work budget. Each layer spends the design’s stitches on the needle points it makes. The top stitches take the same random numbers as without the setting, since an underlay draws none.
  • Joins and roles. Assembly joins the layers as it joins any 2 groups (below), and tags the needle points of each underlay layer underlay.

The needle goes back from a run’s last underlay to its first top stitch, with a jump and its locks where that is farther than the jump length. Each run has one thread, so the design’s colour changes are those it has without the setting. --sort-colours moves the elements that set the toggle as it moves any element with settings, and the runs are made of the elements its order puts side by side.

An element that sews nothing, because it is skipped or too small for a stitch, has no place for its trim or stop. Both are left out, as Ink/Stitch leaves them out, and SC-W0505 says so. So does automatic digitizing of an area it leaves out, which the areas sewn after it cover whole.

A jump lands where sewing resumes, on the tie-in’s first point or on the group’s first point when it has no tie-in, and the needle goes down there before the first stitch. The jump’s own thread is the machine’s business. The plan trims where an element’s trim_after is set, as Ink/Stitch’s does. A PES file also flags every jump as a trim, as pystitch writes Ink/Stitch’s (formats), and whether a machine cuts at a jump is its own setting. At MC-1 the reference machine cut the thread only at thread changes and stops.

Ink/Stitch (read at d59c9ab) joins groups the same way: one stitch from one group to the next within the collapse length, locks and a jump beyond it. It sews that stitch as it is; StitchCraft’s finalize splits it if it is longer than the machine’s longest stitch, which only a min_jump_stitch_length_mm beyond that length can cause.

Lock stitches (ties)

  • A tie-in goes only at the start of a group that the needle jumps to, the design’s first included. A tie-off goes only at the end of a group that a jump, trim, stop or thread change follows, or that ends the design. Groups sewn on from one to the next are sewn without locks between them (REQ-LCK-001).
  • ties says which of those an element’s groups get: both, the tie-in (before), the tie-off (after) or neither. force_lock_stitches adds the tie-off whatever ties says, never a tie-in. It also makes each group of the element end with a jump, and the tie-off is sewn there. That is Ink/Stitch’s rule (read at d59c9ab).
  • Manual stitch is sewn without locks unless force_lock_stitches is set, because its points are placed by hand.
  • A group with fewer than two needle points is sewn without locks: it has no stitch to lock.
  • Lock stitches specifies the lock itself: its shape (lock_start, lock_end), its size and its shortest stitch (0.2 mm).

Several threads in one element

From M10.5 a generator may give each group of needle points a thread of its own, and say whether the group ends one of the element’s colour blocks (stitchcraft_engine::generators::Colour). A colour block is what the generator sews in one thread before it moves on to another colour or another part. A tartan fill will give its colours so from M10.6, and a linear gradient fill from M10.12. A group without a thread of its own is sewn in its element’s, as every group of the other stitch types is.

  • Thread changes. Assembly sews the groups in their order and compares each group’s thread with the one sewing, as it compares 2 elements’ threads. At a change the group before ties off and a colour block starts. The needle then jumps to the next group, which ties in, as the element’s ties allows (REQ-ASM-006). Groups of one colour join as any 2 groups do. The plan’s first colour block has the thread of the first group sewn, which may be a thread of the group’s own. A group without needle points is left out with its thread.
  • Trims. With trim_after on, a trim follows each colour block, after its tie-off, and the element’s last group has its trim and its stop as before (REQ-ASM-007). A group that ends no colour block, such as a tartan’s underlay, has no trim after it. 2 colour blocks of one thread in a row are each trimmed after, with no colour change between them.
  • Order. Stage 0 moves an element of several threads as one, its colours together and in their order. The element has the thread sewing when the thread it starts in is, and leaves the thread it ends in sewing (REQ-AUTO-024, image to embroidery). The order reads each element’s threads before it is generated, from its shape and settings (stitchcraft_engine::generate::colours): its own thread, for each stitch type sewn so far. A stitch type that gives its groups threads of their own will give them there too. The runs of underlays first can ask it which elements are sewn in several threads, which they leave out.
  • What shows them. The machine files, the previews and the report read the plan’s colour blocks, so they show each thread, and VectorCraft’s exporters write them with the same writers (REQ-THREAD-003). A live effect draws every group with its object’s own paints, as VectorCraft paints the geometry a live effect returns (integration).

Ink/Stitch (read at d59c9ab) gives its tartan and linear gradient fills a stitch group for each colour of each part, each with its colour and the element’s trim. It sews their underlay first, in the tartan’s own fill or in the gradient’s first colour, with no trim after it. Its plan compares each group’s colour with the thread sewing, as it compares elements’. Run as a black box with its stitch-plan cache off, its plan of a linear gradient fill of 3 stops has 3 colour blocks, each started by a jump, with a trim after each when trim_after is on and none when it is off. In 2 parts, the colours are sorted so that each sews once, and each part’s colour is trimmed after: 2 trims in each thread. Its tartan sews its underlay in its own fill’s thread without a trim after it, then a trim after each colour.

No stitch type gives its groups threads of their own yet. The engine has no hook for tests, since assembly takes generated elements as its input. A case generates an element as plan does and puts its groups in threads of their own. It then assembles and finalizes the element as plan does (stitchcraft_testkit::designs::threaded). The order’s cases give it each element’s threads directly.

Origin, stop position and turn on export

The finished plan is in hoop coordinates: the design’s origin goes to the hoop’s centre, (0, 0), where the needle starts. The origin is the design’s own or else the centre of the box around every point where the needle goes down (REQ-ASM-005). Assembly builds the plan in the design’s coordinates, and finalize moves it once it has left out the points the machine cannot sew, so the box is the finished plan’s, as in Ink/Stitch. A design’s stop position adds a jump to it before each Stop. At the stop position the frame is clear of the needle for an appliqué or a check, and sewing resumes with a jump back. The plan’s bounds take in that jump, and the hoop check measures them (SC-E0701).

An SVG file gives both with Ink/Stitch’s origin and stop_position commands, a VectorCraft document with objects named stitch:origin and stitch:stop-position (M8.8). Each is a point anywhere in the document. Ink/Stitch’s command is where its symbol is placed, and a marker is at the middle of the box round its anchors. A file with 2 origins, or 2 stop positions and a stop, is an error (SC-E0819), since which one counts isn’t known. Ink/Stitch doesn’t write a machine file of it either.

Once the origin is at the hoop’s centre, the design’s turn on export turns the plan about it, by its degrees, right for a positive number (M8.9). It is Ink/Stitch’s design setting rotate_on_export, for a machine that doesn’t turn a design to fit its hoop, which the Design Settings filter keeps with a VectorCraft document. Ink/Stitch’s writer turns the machine file the same way, stop position jumps included. The hoop check measures the turned plan, as the machine gets it. A whole number of quarter turns moves each coordinate to the other axis and rounds nothing (stitchcraft_engine::design::Turn).

5. Finalize

Finalize fits the plan to the machine profile (stitchcraft_engine::finalize), and a plan that plan returns can be written as it is. Generators sew within the machine’s limits where their settings let them. What is left to fit comes from joining groups and from settings the machine cannot follow.

  1. The shortest stitch of each needle point is its element’s: the one its generator used, so finalize never thins what the generator spaced. That is the element’s min_stitch_length_mm, else the design’s min_stitch_len, and never shorter than the machine’s (profile.min_stitch). Where one element’s stitching runs straight on into the next, the stitch between them can be anything up to the collapse length, 0 included. Within each run of stitches, from where the needle lands to the next jump, trim or stop, a needle point less than its shortest stitch from the one before is left out. The stitch then runs on to the next point. The run’s first and last points and lock points stay, and the points before them are left out instead. Elements sewn over each other can bring the last point or a lock point within the shortest stitch of one that stays before it, once the points between are left out. It is then left out itself, the points before it stay, and a trim or stop after it happens where the needle now is. So is a point where the needle already is, which would sew in place. Only the run’s first point always stays. A stitch into or out of a lock point is a lock stitch, whose shortest is 0.2 mm (REQ-PLAN-002). A stitch is left out unless it is still long enough once the plan is moved to the hoop’s centre (step 3): the move rounds each point to the nearest double, which may shorten a stitch by a few billionths of a millimetre. A stitch at the very edge of what counts as long enough would otherwise fail the check after the move. SC-I0504 says how many points were left out (REQ-FIN-001). The rule is one function, which a generator that joins pieces of its own also applies, as a tatami fill does to its rows and the travel between them, so that finalize finds nothing of its stitches to thin. A satin column joins its parts by rules of its own instead, since the end of a top stitch must not move (satin).
  2. The longest stitch. A stitch longer than profile.max_stitch is split into the fewest equal parts no longer than it (SC-I0703, REQ-FIN-001). Such a stitch comes from a stitch placed by hand, a custom lock’s long step, a satin column wider than the machine’s longest stitch, a tatami fill whose max_stitch_length_mm is longer than it, or a move sewn on under a min_jump_stitch_length_mm that long. Each part counts against the design’s stitch budget.
  3. The hoop’s centre. The fitted plan is moved so the design’s origin is at the hoop’s centre, and turned about it by the design’s turn on export (origin, REQ-ASM-005).
  4. Colour limits: colour changes and stops above what the format the plan is written in records → SC-E0601. That is the profile’s own, or the one --format or an exporter writes, planned for with MachineProfile::writing: a DST file records 999 colour changes, where the PE800’s own PES records 255.
  5. Hoop: a design larger than the hoop → SC-E0701, with a rotate-to-fit fix when rotating 90° would fit. When a design’s origin is far from its middle, a design smaller than the hoop can cross the hoop’s edge. That is SC-E0701 as well. So is a stop position past the edge, which the message names. The size is the stitches’ own. For a design that cannot be sewn, SC-E0701 is the only message about its size. Otherwise, larger than the comfort zone → SC-W0702 (REQ-FIN-002).
  6. The end is the plan’s structure: the machine ends after the last block.

After an error at any step, plan returns no plan, and the error’s diagnostic says why.

Splitting jumps longer than a format can encode in one record is not done here: it is the encoder’s job, because the limit is a property of the file format, not of the machine.

Ink/Stitch (read at d59c9ab) removes short stitches once, over the whole plan: an entry no farther than its shortest stitch (the element’s min_stitch_length_mm, else the design’s min_stitch_len_mm, 0.1 mm unless the file sets it) from the last one kept is dropped. It keeps lock stitches, the stitch right after a jump, and stop, trim and colour-change entries. A jump itself can be dropped. Nothing is split. StitchCraft uses the same shortest stitch for each element as Ink/Stitch, but never one below the machine’s (0.3 mm on the Brother). It keeps the ends of each run and splits stitches the machine cannot sew: a deviation (DEV-FIN-001), because a file can sew differently in the two tools.

6. Check

The plan invariant checker (stitchcraft-plan::invariants, the same code conformance level L0 runs) validates the result. A violation is a bug in StitchCraft: plan returns no plan and reports SC-E0009 internal check failed (REQ-FIN-003). The command line then does not write a machine file. It writes a bug-report bundle that reproduces the failure (REQ-CLI-002). The conformance suite has a case for every invariant.

7. Incremental and parallel planning

  • Cache: a group is keyed by (element shape hash, params hash, neighbours, seed, engine version). The VectorCraft live effects already cache per object; the CLI and future panels reuse the same key.
  • Parallelism (native only): elements are generated in sewing order, each seeing its neighbours (ADR 0014). Reading parameters and recognizing shapes depend on the element alone. That work may run in parallel with rayon behind the CLI’s parallel feature. Its results are joined in document order, and the output is then identical to a sequential run. The wasm plug-in stays single-threaded.
