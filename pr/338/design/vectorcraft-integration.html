StitchCraft

VectorCraft integration

How StitchCraft lives inside VectorCraft: what VectorCraft offers today, how we use it without changing VectorCraft (phase 1), what we propose upstream (phase 2), and how an in-tree integration would look (phase 3).

VectorCraft snapshot reviewed: main at 89ea46c (2026-10-08), version 0.6.0, and its plug-in API again at 8bf090b (2026-10-24), after 0.16.0, at v0.17.0 (2026-10-25) and at v0.18.0 (2026-10-28). File references below are to the first unless a version is named. The compatibility gate tests the plug-ins against each VectorCraft release and branch.

2. Extension points that exist today

Plug-in ABI v1 (crates/plugins, docs/plugins.md)

  • Sandbox: a core WebAssembly module run by wasmi 2.0, no imports at all (no WASI, clock, file system or randomness). Exports: memory, vc_abi_version() → 1, vc_manifest(), vc_alloc(size), vc_run(input, len, params, len). Input and output are JSON.
  • Kinds: object filters (read selected paths and compound paths — geometry, fills, strokes, opacity — and return updated or new objects; one undo step) and live effects (rewrite one object’s geometry every time it is drawn, cached by plug-in, parameters and input geometry). From 0.14, exporters write the whole document in a file format of their own, listed by File › Export › Export As.
  • Parameters: manifest schema with number, int, bool, choice; at most 64 parameters (MAX_PARAMS, crates/plugins/src/manifest.rs:11) and a 64 KiB manifest; no labels, units, groups or conditions until 0.14, and the dialog shows the parameters’ names. From 0.14: string and numberList too, up to 256 parameters with at most 64 outside groups, and each parameter’s label, unit, group, help, helpUrl and visibleWhen.
  • Limits (crates/plugins/src/runtime.rs): module ≤ 32 MiB; memory ≤ 512 MiB; output ≤ 64 MiB JSON; fuel 50 M instructions + 4,000 per input byte; wall clock 60 s per filter run and 5 s per live-effect run (crates/plugins/src/effect.rs), with a fresh instance for each call. An export gets 10 G instructions and 300 s (0.14). From 0.17 a filter that declares "budget": "heavy" gets 1 G and 300 s, once the user allows it at install, and runs in the background. From 0.23 only a person allows it: with OK in the app’s dialog, or by starting the command line with --allow-plugin-grants. From 0.18 a run pays nothing for compiling the functions it calls, which wasmi does at each one’s first call. Before, a first run paid, and could stop with most of its budget left when the 20 M-instruction slice it was in ran out while a function compiled. From M13.2 on, the gate’s Level B found 0.17.0’s command line stopping the PES exporter so on the test sheet TS-04, an export that takes 34 M instructions in 0.18.0’s host.
  • Live-effect input is the object’s geometry: type, path, fillRule, bounds. From 0.14 it holds the object’s fills and strokes too, read only, each stroke with its width, and from 0.15 its join, cap and miter limit. _context.item says whether the effect is on the object or on one of its paints. The objects beside it are still not given.
  • Filters are given each stroke’s join, cap and miter limit and each object’s effect records, and may return effect records (0.15). From 0.16 a filter keeps up to 1 MiB of data with the document (documentData).
  • Persistence: applying a live effect stores {"id": "plugin.<id>", "params": {…}} in the object’s appearance (Effect { id, params: serde_json::Value, visible }, crates/doc/src/appearance.rs). Documents keep the record when the plug-in is missing and draw the object unchanged.
  • Not in v1: tool plug-ins, panel plug-ins, host callbacks (progress, cancel), importers, live effects that change paint. File-format plug-ins came with the exporters (0.14).

Other facts that shape the design

  • No generic per-object metadata. Node has attrs: Option<Box<ObjectAttributes>> with only centre display, image map, URL and note (crates/doc/src/node.rs). The effect record is therefore the right place for embroidery parameters.
  • Document-level foreign data lives in Document.unknown (used for the perspective grid and brushes), preserved on round trips (crates/doc/src/lib.rs). From 0.16 the data filters keep with a document is there too, under pluginData.
  • SVG import keeps only the attributes it understands. The importer looks attributes up by name (presentation attributes, references, names such as inkscape:label) and has no place to keep unknown ones (crates/svg/src/import.rs), so an Ink/Stitch SVG opened in VectorCraft up to 0.16 loses its inkstitch:* parameters. From 0.17 VectorCraft keeps attributes in other applications’ namespaces from SVG import to SVG export, and reads none of them. SVG export can embed the whole native document (vectorcraft:document) when editing data is preserved.
  • Export formats are a static table (FORMATS in crates/engine/src/cmd/fileio/mod.rs). From 0.14 an exporter plug-in adds a format to it, plugin.<id>, which is how StitchCraft can add PES.

The adapter makes the ids from it, a plug-in’s with plugin_id and its live effect’s with effect_id, and effect_name reads one back. The plug-in crate and the compatibility gate use the same functions. A live effect’s id ends with its stitch family’s (stitchcraft_params::Family::id). Manifests are generated from the parameter registry; a test validates each against VectorCraft’s manifest rules (id charset, the most parameters, names, ranges, and from 0.14 the keys that say how the dialog shows a parameter), so a manifest VectorCraft would refuse fails the tests before a release.

Modules. The plug-in crate builds one module for each family, chosen by a Cargo feature named after the family: stroke, satin or fill, one for each machine format, by its extension: pes or dst, and one for each filter: settings, stroke-to-satin, testsheet, route-satins, route-runs and tartan. The feature lettering builds the Lettering effect. Without one it builds M0.6’s hello effect. The modules contain the same code, which the native tests run whichever it is, and the feature only picks the manifest and the run that vc_manifest and vc_run serve. cargo xtask compat contract builds every module, notes their sizes and loads them into VectorCraft’s host.

Manifests. A family’s manifest is made from the registry when VectorCraft asks for it, so a parameter added to the registry shows in the dialog without another change. A key that several families declare, each its own way, is in each family’s manifest as that family declares it (parameter registry, rule 7). VectorCraft’s parameters are numbers, whole numbers, toggles and choices, and each always has a value. VectorCraft 0.14 adds texts and lists of numbers, which older releases refuse. A record stores every declared parameter, at its default when the user leaves it. So a parameter is declared when one such value means what the parameter means:

  • a length, an angle, a percentage or a number as a number in its range, and a count as a whole number;
  • a list or a pair whose default is one value as that value, which stands for the whole list or both sides, as in Ink/Stitch;
  • an optional length that 0 leaves unset as a number from 0;
  • a tartan’s sett as a text, from M10.7 (below).

The other texts, seeds, and settings left empty to take another’s value keep their defaults. In the registry today they are the custom locks’ steps, random_seed, a fill underlay’s angles, and a satin’s zigzag underlay insets and its shortest random split. A choice leaves out the options that a text spells out, which are the custom locks, and fill_method leaves out Ink/Stitch’s legacy fill, which StitchCraft sews as a tatami fill (REQ-FILL-005). satin_column belongs to the effect, which sets it from its family. From M13.26 the fill’s dialog has turn_stitches, the switch that automatic digitizing sets on its own fills, and every stitch effect’s dialog digitized_as, last of the settings every element shares: VectorCraft admits an effect record only with the parameters its manifest takes, and an expanded part sets both (REQ-VC-035, Expand). The Auto effect’s dialog leaves out the settings of the registry’s Advanced group, which are the bounds of the rules and the 2 limits of the cover’s measure (M13.21), the base layer’s offset, and the 4 limits of how thick a design sews (M13.29), how far outlines are smoothed (M13.52), and how far an area lies under a part’s satin column (M13.55). The last 2 are off unless --set asks for them. The switch that sews an outline round each fill has a row since M13.28, in the offset’s place. The dialog opens with the group that declares the family’s method. The groups only the family uses, for its default method, come next, then those it shares with the other families, then those of its other methods, such as the zigzag stroke’s. The settings every element shares come last, as in Ink/Stitch’s dialogs.

The fill dialog’s 65 settings

M10.9’s stitch positions made the fill dialog 64 parameters, the most that VectorCraft 0.12 and 0.13 take in a manifest. M10.10’s strategies need guided_fill_strategy in the dialog: VectorCraft keeps only the settings a manifest declares, so a strategy the dialog doesn’t hold can’t be set in a document at all. It is the 65th.

VectorCraft’s rule from 0.14 is 256 parameters, at most 64 of them outside groups, since a longer dialog is sorted into sections (MAX_PARAMS and MAX_UNGROUPED in its crates/plugins/src/manifest.rs, and “Parameters” in its docs/plugins.md). Every setting of a StitchCraft dialog is in its registry group, a section of the dialog, and the fill effect installs only from 0.14 for its sett’s text. So the manifest check now follows VectorCraft’s own rule (REQ-VC-023):

  • at most 256 parameters, and at most 64 outside groups;
  • more than 64 only in a manifest that VectorCraft 0.12 and 0.13 refuse anyway, an exporter’s or one with a text, so that no effect those releases install grows past what they take.

visibleWhen hides rows without lowering the count, so it was no way out. The alternatives were weighed and turned down:

  • A dialog of its own for the guided fill, as another effect. A fill could then not change its method in place, and a document would hold 2 kinds of fill effect for one registry.
  • The strategies left to files, set in an SVG file and sewn by stitch export, with a coded note in VectorCraft. A design drawn in VectorCraft could then never offset or buffer its guide.
  • Another setting left out to make room. Each of the 64 is one a fill method needs, and the next setting would ask the same question again.

The compatibility gate installs the fill effect in every supported release from 0.16, so a release that took fewer would fail it (compatibility gate).

A tartan’s sett

A tartan’s sett is one setting, tartan, an object of JSON whose code lists the stripes (tartan fill). M10.6’s fill dialog offered the tartan fill with its numbers alone, tartan_angle, rows_per_thread, herringbone_width_mm and stop_at_ending_point, and a tartan fill made in VectorCraft sewed Ink/Stitch’s default sett. M10.7 decided how VectorCraft sets a sett, and chose both of the ways open to it (REQ-VC-021):

  • The fill dialog shows the sett as text, its row labelled Sett and shown for the tartan fill alone. A live effect is given only the settings its manifest declares, and VectorCraft drops a record’s other keys before it runs the effect. So without this row no preview could sew a sett of its own, whatever wrote it. The row also shows the sett an Ink/Stitch file brought, and takes one pasted in. With it the fill dialog had 63 parameters, and it is the only text a dialog declares (manifest::TEXTS). A text is also why the fill effect installs from VectorCraft 0.14, where a dialog may declare more than 64 settings (below).
  • StitchCraft Tartan, a light filter, writes the row from what a person has, a palette code or a threadcount in the register’s colour letters, with the width of a thread, the sett’s turn, its scale, how far it is moved and the width up to which a stripe sews as a run (apps/stitchcraft-vc-plugin/src/tartan.rs). It is Ink/Stitch’s editor reading a code (the editor). A selected path whose own first StitchCraft effect is the fill effect gets the tartan fill and the sett, its other settings kept as VectorCraft gave them. A path with no StitchCraft effect gets the fill effect with those 2 settings, and VectorCraft fills in the rest. A filter can’t warn, so a code it can’t read, letters the register uses for no colour, a code without a stripe, a setting longer than the row’s 4,096 characters, and a selection without a path to take the sett leave the drawing as it was, with SC-E0821. Records a filter gives are kept from 0.15, and before it the filter declines with SC-E0813.

The rejected ways each failed a part of the job. The filter alone would write a key the fill’s manifest doesn’t declare. The preview never gets such a key, and the canvas would show Ink/Stitch’s default sett while File › Export sewed the filter’s. With the row alone, a person would write an object of JSON by hand on one line. A threadcount, the form the register gives a sett in, wouldn’t read there. A filter that drew the stripes as objects of their own would lose the weave, which comes from routing every colour’s rows over the whole shape.

What it costs. A text is a kind of parameter VectorCraft 0.14 brought, and 0.12 and 0.13 refuse a manifest with one whole. So from M10.7 the fill effect installs from VectorCraft 0.14, as the exporters do. Those 2 releases don’t export a machine file either, so a fill made there was only ever a preview.

The Test Sheet filter drew TS-17B from M10.7, each tartan’s sett in its fill effect’s record as the row’s text, and from M10.12 each of its gradients as a gradient paint (below). From M10.9 the sheet’s guided leaf copies a guide line. Drawn into a document, the guide would be a stitch:guide marker grouped with the leaf, and a filter doesn’t make groups. Only stitch testsheet draws TS-17B now. The filter still draws a linear gradient fill with its gradient paint, though no sheet it draws has one.

How the dialog shows them (REQ-VC-012, M6.10). From 0.14 a parameter can say how the dialog shows it, and the plug-in says all of it from the registry (apps/stitchcraft-vc-plugin/src/dialog.rs):

  • Its row has the registry’s label, and the unit of its kind of value: mm, % or °.
  • The registry’s groups are the dialog’s sections, as they are the headings of the reference pages. VectorCraft draws a section where its group first appears, with every row of the group in it. Each group’s rows come together in the manifest, and a release before 0.14 shows them in the same order.
  • Its help is the registry’s help as plain text, cut at a sentence within VectorCraft’s 1,000 characters. A choice’s help ends with what each option means, by its label in the registry: VectorCraft’s drop-down list shows the ids that designs store, such as tatami_fill. Its help page is its entry in the parameter reference on the docs site, the book of main (dialog::SITE_URL). The docs check finds the page and the heading each manifest links to.
  • Each row shows only while the method is one the parameter applies to. Where the registry shows a setting only with some values of another, as its when says, the dialog does too: the length variation of a random stitch length shows while that is on, and a satin’s staggers for staggered splits. Rows that nothing in the dialog would show are left out. VectorCraft gives the plug-in the value of a hidden row as well, so what the dialog shows never changes what sews.
  • The plug-in’s own parameters, the preview level and the exporters’ 2 options, have a label, help and a page too.

A release before 0.14 ignores these keys, since its ParamSpec reads a parameter’s type, range and default and lets other keys pass (crates/plugins/src/manifest.rs at 0.12.0). Its dialog shows the keys and every parameter, as it did. The compatibility gate’s pictures of the dialogs are taken in the pinned release’s window, and the window probe checks that each shows the rows the manifest shows at the defaults, by label, each with the control of its kind.

What a live effect shows. A family’s effect sews its object with the engine’s generate, on the reference machine and with no neighbours, as one object of a design. It returns the stitches as geometry, the exact level below. When it can’t show stitches, it gives back why. VectorCraft then draws the object as it is and shows the message as the plug-in’s last error. That happens when the object cannot be sewn or sews no stitch, with the message that says why. A drawing that vanished instead could not be clicked to change the setting that emptied it. ABI v1 has no way to pass VectorCraft the warnings about stitches the effect shows, and stitch export reports them. How much of the stitches it shows, within what VectorCraft lets it spend, is its preview level (below).

The stroke an effect follows (REQ-VC-010, M6.8). A satin column drawn as one path and a zigzag stroke are as wide as their stroke. From 0.14 VectorCraft gives a live effect its object’s fills and strokes, and a stroke or a satin effect on the object follows the topmost stroke that has a paint and a width. It reads the stroke’s width, and from 0.15 its join, cap and miter limit, with the reader’s own code (stroke_style in crates/stitchcraft-vectorcraft). stitch export follows the topmost stroke VectorCraft draws, and the 2 can differ in 2 ways. VectorCraft gives a live effect every stroke of its object without its opacity or whether it shows, and gives it none of the paints of the groups around it. Given no stroke, before 0.14, for an object without one, or where only a group’s stroke paints it, the effect leaves a satin column drawn as one path and a zigzag stroke as they are, with SC-I0810. An effect on one of the object’s fills or strokes leaves the object as it is too, with SC-I0810: stitch export doesn’t use such an effect (SC-W0807).

The workflow

  1. Draw the art in VectorCraft as usual.
  2. Select an object → Effect › Plug-ins › StitchCraft Fill (or Stroke / Satin) → set parameters in the generated dialog. The parameters are now stored on the object (undoable, saved in the .vectorcraft file) and the object shows a stitch preview.
  3. Save the document.
  4. stitch export design.vectorcraft -o design.pes --preview design.png writes the machine file, for the machine --profile names, or else the one the document keeps (below), or else brother-pe800-5x7, and a picture of what will sew. It says what the reader left out or changed, with the engine’s warnings. stitch export is another name for stitch plan, which reads a VectorCraft document (.vectorcraft, .drawcraft, or a .vctemplate template) as it reads an SVG file (REQ-VC-008), and --report adds the JSON report. A bug-report bundle includes the part of the document the reader reads, which is its JSON without the images after it. Its replay reads that part the same way. From VectorCraft 0.14, File › Export › Export As writes the same file with StitchCraft’s exporters, without saving first (below).

Stitching order is paint order (bottom first). Hidden objects are skipped, as VectorCraft draws nothing for them, and locked objects are stitched. Thread colours come from the object’s fill for a fill, and from its stroke for a stroke or a satin column, as in Ink/Stitch, mapped to the profile’s palette.

From M10.15, objects next to each other in paint order and in one thread, whose StitchCraft effects set underlays_first, sew their underlays before their top stitches (underlays first). The toggle is a row of every stitch family’s dialog. Set on a group’s effect, it applies to every path in the group (REQ-VC-006). A live effect sews its object alone, so a preview doesn’t show the order, and stitch export --preview draws what sews.

Exporters: File › Export writes PES and DST

VectorCraft 0.14 added exporter plug-ins (the RFC’s P1). File › Export › Export As lists each after the built-in formats by its name, and document.export writes one for a path with the extension it lists. VectorCraft gives the exporter the document as a native .vectorcraft file’s JSON, as document.save writes it but without the data of images of 8 KiB or more, with the parameters of the dialog it shows when the file is picked, and the file’s extension and name. The exporter returns the file in base64, with warnings for the user, or declines with a message, and then nothing is written (VectorCraft’s docs/plugins.md, Exporters). The VectorCraft adapter’s encoder (stitchcraft_vectorcraft::base64) writes it, as it writes the picture stitch plan gives VectorCraft’s command line to trace (image to embroidery).

M6.9 makes StitchCraft’s formats exporters (REQ-VC-011, apps/stitchcraft-vc-plugin/src/export.rs). There are two, PES embroidery (StitchCraft) and DST embroidery (StitchCraft), each a module of its own, and a VectorCraft before 0.14 refuses to install them. An exporter writes the file stitch export writes of the document:

  • It reads the document with the same reader and plans it with the engine for the machine its profile option names, written in its own format, whose colour changes the plan keeps to (REQ-PLAN-006). The design takes the file’s name. The option’s default, document, is the machine the document keeps, or brother-pe800-5x7 when it keeps none, as stitch export plans it without --profile (below). Reading the file back, as stitch export does, stops it at a writer’s bug (SC-E0009). The file has every thread of the plan, those of an element sewn in several among them (REQ-THREAD-003). The budget is stitch export’s own too. Its auto option, on by default since M13.8 (stitchcraft_vectorcraft::AUTO_BY_DEFAULT), digitizes the objects without StitchCraft effects, as stitch export does without a switch, and sews them in the order StitchCraft chooses. Off, it is --no-auto. The exporters have no switch like --sort-colours, and the objects with effects keep their order among themselves (image to embroidery). Level B of the compatibility gate exports a document with VectorCraft’s command line and checks that the files are stitch export’s, byte for byte.
  • What stitch export says, the export says as its warnings, one line each, naming the object and with the hint after it. VectorCraft shows 100 of at most 500 characters each, so of more the last says how many more stitch export lists. It cuts a longer line in the middle of a word. The export ends such a line at its last whole sentence that fits. SC-W0913, the longest warning, is worded to fit with its hint: on a traced picture it has fewer than 500 characters.
  • When anything said is an error, the exporter declines with the first, after how many there are, and VectorCraft doesn’t write the file, as stitch export doesn’t (REQ-CLI-003). VectorCraft shows the first 300 characters of a decline, after plug-in failed:.

An export may run 10 billion instructions, and 4,000 more for each byte of the document, and 300 seconds. The engine’s budget is stitch export’s, so a design that needs more is stopped by VectorCraft with its own error, plug-in exceeded its instruction budget, and stitch export writes it. The contract test req_vc_011_a_fill_of_the_whole_hoop_exports_within_vectorcraft_s_limits measures the largest designs the reference machine sews (VectorCraft 0.16.0 to 0.18.0 alike, 2026-10-29):

About 140 fills of that size are as many as an export can plan, which few drawn designs for a home machine’s hoop reach. A traced photo does, and an export that finishes says what exports it. The test sheets drawn as designs export within 17 % of what an export may run, once the Test Sheet filter has drawn them into a document (below). A live effect is given no warnings channel, and VectorCraft asks an exporter for no picture: stitch export --preview still draws what will sew.

What M13.33 can bring down. The 3 largest costs, in order:

Tools: Stroke to Satin and Test Sheet

M6.12’s 2 filters draw objects with StitchCraft’s effects, which a filter’s output may hold from VectorCraft 0.15 (the RFC’s P8). The VectorCraft adapter reads what a filter is given and writes what it gives back (stitchcraft_vectorcraft::filter). A paint, an effect record and an opacity given back are written as the JSON text VectorCraft gave, since VectorCraft keeps a paint’s swatch, and a record as it was, only when they come back unchanged, which it tells by their values. A path is written in points, each coordinate the shortest decimal that reads back to it. VectorCraft admits a new effect record as effect.apply would apply it: a StitchCraft effect’s only while its plug-in is installed, its parameters filled in to their defaults.

Stroke to Satin (REQ-VC-014, apps/stitchcraft-vc-plugin/src/stroke_to_satin.rs), Ink/Stitch’s Stroke to Satin, once Convert Line to Satin, makes each subpath of each selected path that has a stroke into a satin column drawn with its rails and rungs. The line is the column’s centre line, as wide as the stroke a satin effect on it would follow, with that stroke’s join. The engine makes the rails and rungs it makes of such a column when it sews one (REQ-SAT-016, REQ-SAT-017), and draws them as straight lines, each rung longer than the gap between the points it pairs by a hundredth of it at either end, so that it crosses the rails (satin generators). Read back, the column pairs the same points, so it sews as the line did. A column of 2 rungs or none gets a rung at an end too, since Ink/Stitch’s rule would read the 2 longest lines as its rails (DEV-SAT-007). The rung goes across the column’s start, or across its end where the satin effect’s push compensation lengthens the start. Push compensation lengthens the rails before they are cut, so a rung across a lengthened end would make the part added there a section of its own.

Each column is a compound path without fills. Its stroke is the line’s paint one CSS pixel wide, which shows the rails and draws the satin effect’s stitches thin. The first column takes the object’s place, and the others go above it with its opacity. The satin effect takes the place of the object’s first StitchCraft effect, with the line’s satin settings or the defaults. The object’s other StitchCraft effects are left out, and its other effects kept. An object the satin effect already reads as rails is given back as it is. Tools: the routing filters

From M10.4 and M10.13, 2 filters in Object › Plug-ins route the selection with the engine’s routing function, as Ink/Stitch’s tools route theirs (routing tools, ADR-0017). StitchCraft Auto-Route Satin Columns (<ns>.route-satins) routes satin columns and the strokes among them, and StitchCraft Auto-Route Running Stitch (<ns>.route-runs) routes strokes.

What they read. VectorCraft gives a filter the selected paths in paint order, with the paths in the selected groups and layers, and Preserve order keeps that order. Each path routes as a satin column when the first of its own StitchCraft effects that is on is the satin effect, and as a stroke when it is the stroke effect. Auto-Route Running Stitch takes the strokes alone, and leaves a satin column as it is, as Ink/Stitch’s tool leaves one. VectorCraft gives a filter each path’s own effect records, and none of its groups’. So a path that sews by a group’s effect (REQ-VC-006) stays as it is, as Ink/Stitch’s tool leaves a fill. So does a path without a StitchCraft effect of its own. A selection with nothing to route is refused with a coded error, whose hint says to put the effect on the paths themselves. Objects named stitch:route-start and stitch:route-end among the paths give the route’s ends (start and end).

What they write. A column’s piece is a compound path of its rails and rungs with the column’s satin effect, drawn as Stroke to Satin draws a column. A stroke’s stretch, and a run under the others, is a path with the stroke effect, which for a run under a column keeps the column’s underlays_first, and for a run under the others its stroke’s (order). Each is painted with its element’s stroke and named as Ink/Stitch names it, and Trim jump stitches turns on trim_after in the effect of the piece before a long jump. In one undo step, the pieces replace the paths they come from and the markers used. A filter can’t make a group, where Ink/Stitch puts its route in a new group after the last element. So the pieces go in their sewing order where the topmost path routed was, in its group or layer. With Preserve order, Ink/Stitch moves each piece to the end of its element’s group, and the filter puts the pieces of each path, the runs along it among them, where the path was, in sewing order. With Keep original paths, an option of Auto-Route Satin Columns alone, the paths and markers stay as they are, and the route goes above the topmost path. A group the run leaves empty stays in the document. Each piece keeps the other effects of the path it comes from, as Stroke to Satin keeps a line’s. Its paint is that path’s stroke 1 CSS pixel wide, or black for a path without a stroke.

Budget. Both are heavy filters (VectorCraft 0.17), as Stroke to Satin is. Each run gets 1 G instructions and 300 s, once the user allows the filter at install, and runs in the background, with no preview in its dialog. Stroke to Satin’s run, which makes a column’s rails from its centre line, took up to 233 million instructions for one line (above). A route makes the rails of every column drawn as one path that it routes. Reading .vectorcraft files (stitchcraft-vectorcraft)

stitchcraft_vectorcraft::read turns a .vectorcraft file into a design, and reports what it left out or simplified, as the SVG adapter does for SVG files. It reads the format as VectorCraft documents it (crates/format and the types crates/doc saves) and links none of VectorCraft’s crates. VectorCraft versions 0.7.0 to 0.12.0 were read for this design.

The container. A file is JSON, compressed with gzip when its first two bytes are 1F 8B. VectorCraft compresses from format 3 on, but the adapter reads any version either way. In format 4, images and other large data can follow the JSON, behind the marker \n\0VCBLOBS\0. JSON text never holds a NUL byte. The JSON ends at the first one, and nothing after the marker is read. The top level must say "format": "vectorcraft", or "drawcraft", VectorCraft’s earlier name, and hold a document. Formats 1 to 4 read alike: points as {"x", "y"} or [x, y] in any of them. A newer format is read as far as it goes, with SC-W0803, where VectorCraft’s own readers refuse it.

Limits. At most 64 MiB of JSON, unpacked, as for an SVG file, and the command line reads at most 64 MiB of any file (REQ-CLI-005), images included. A gzip stream is unpacked only up to the marker, and no further than the limit. Nesting deeper than the JSON reader allows (128 levels, about 40 levels of groups) refuses the file. VectorCraft itself keeps 32. The JSON is read into the few things the adapter uses, and the rest is skipped as it is read: images and previews are never kept, and of a text only its characters and their fill. Every object, appearance item, effect and anchor charges the budget, and so does each element for its copies of the object’s path, name and settings. An object’s name goes into each element made of it, and a group’s StitchCraft settings into each element of the paths in it. Those copies come to at most 64 MiB, as much as the JSON read. Each element’s copy of its object’s path takes 56 bytes a segment, and a long path under many paints would hold far more than the file: 4 MB drawing 2,500 fills on a path of 200,000 anchors would hold 28 GB before the budget ran out. So the copies of paths come to at most 32 bytes for each byte of JSON read, which an object’s fill and stroke on its most compact path keep well within. A file whose copies come to more is refused with SC-E0806. A clip group’s clip is held once, shared by the elements it cuts, and costs each of them a unit for each of its segments.

Coordinates. VectorCraft keeps every path in document coordinates. Moving or scaling a group moves its paths’ anchors, so layers, groups and compound paths have no transform. Coordinates are points, 1/72 inch, with y down, and the adapter multiplies them by 25.4/72 into millimetres. The document’s origin stays the origin. It is the canvas’s origin, through which a cross stitch fill’s grid passes (canvas_grid_origin, cross stitch), decided in M10.1. A new document’s first artboard has its top left corner there, and moving an artboard leaves the grid where it is. Coordinates are read exactly, as VectorCraft reads them, from their text in the JSON. An anchor’s handles are absolute positions. A missing handle, or one within a billionth of a point of its anchor, leaves that end of the segment straight, and a segment without handles is a line.

What is stitched. The layers in order, bottom first, and in each its children in paint order:

  • Paths and compound paths are the art. A compound path’s children are one shape, with the compound’s appearance and fill rule.
  • Groups and layers pass their children on, and their StitchCraft effects with them (below). A clip group’s or a clipping layer’s art is cut to its clipping object, as VectorCraft clips it (below).
  • Hidden objects, and everything in them, are left out without a word, as VectorCraft draws nothing for them. So are objects and paints of opacity 0, paints turned off and strokes of width 0.
  • Objects and layers named stitch:ignore, and everything in them, are left out with SC-I0811. Start and end markers are never stitched (commands).
  • Template layers, layers that don’t print, and guides are left out with SC-I0809. VectorCraft shows them, dimmed or as guides, but prints and exports none of them.
  • A Shaper group’s sources are left out. The group shows the shapes it makes of them, and keeps them as its first child, transparent. The Layers panel’s Make Clipping Mask (layer.clippingMask.toggle) puts a Shaper group’s clipping object before them.
  • Text with StitchCraft’s Lettering effect sews in an embroidery font (lettering). Without the effect, text under automatic digitizing sews in the default embroidery font, or a bold text in the bold font where it sews at the text’s size (below, fonts). Other text is left out with SC-W0807, whose hint names the effect and Type › Create Outlines.
  • Images and symbols, and the objects VectorCraft computes as it draws them (blends, envelopes, meshes, repeats, placed documents and VectorCraft’s Intertwine objects), are left out with SC-W0807. The message names VectorCraft’s command that makes paths of them. So is a kind of object this version doesn’t read.

Paints and threads. An object without StitchCraft’s effects is stitched as Ink/Stitch stitches an SVG shape. Its visible fills are filled, in the appearance’s order, and its visible strokes then have a running stitch each. Since M13.1, read with --auto (stitchcraft_vectorcraft::read_with), the elements of an object are automatic instead when neither it nor a group or layer around it has a StitchCraft effect (image to embroidery, REQ-AUTO-001). StitchCraft then chooses their stitches by its rules. Since M13.7 StitchCraft’s Auto effect makes them automatic without the switch (REQ-VC-016). It is read where a stitch effect is read, on the object or on a group or a layer around it, the nearest first, and its parameters are the object’s settings of the rules. A stitch effect says how an object sews, so an Auto effect beside one on the same object or group isn’t used, and SC-W0807 says so. Read with --sort-colours, the objects with effects sew in the order StitchCraft chooses too (REQ-AUTO-011). A stroke’s cap is read with its width and join, and an automatic line’s stitches follow its round or square caps. Of a line sewn across its width, the reader names the alignment inside or outside a closed path and the width profile, which its stitches don’t follow (SC-W0807, REQ-AUTO-005). The thread’s colour is a solid paint’s colour, with CMYK and grey converted by VectorCraft’s formula without colour management ((1 − c)(1 − k) and 1 − k) and Lab through sRGB. A gradient gives the colour of its first stop VectorCraft shows, of an opacity other than 0, with SC-W0807 unless every stop is shown in that colour. With fill_method set to linear_gradient_fill, the fill takes that colour without a word and sews the gradient (below). Gradients whose stops are all of opacity 0 paint nothing, as those without stops do, and are left out without a word. A pattern gives black, with SC-W0807. A stroke’s width, in points, and its join, with its miter limit (10 when the file omits it, as VectorCraft draws it), shape a satin column drawn as one path. A stroke drawn with a brush is stitched along its path, without the brush’s art, with SC-W0807.

What VectorCraft draws of a stroke that its stitches don’t follow is named with SC-W0807, and the message says how to stitch it, usually with Object › Path › Outline Stroke:

  • A stroke’s arrowheads are not stitched, and a dashed stroke is stitched along all of its path. A dash pattern that VectorCraft draws solid, with a length below 0 or that is not a number, or only 0s, is no dash.
  • A stroke painted below a fill is sewn after the fill, over it.
  • A satin column or a zigzag made of a stroke is as wide as the stroke all along and centred on the path. VectorCraft draws a closed path’s stroke inside or outside it when it is aligned so, and varies its width along a width profile. It also caps an open path’s ends with round or square caps. A running stitch along the path is the same whichever way the stroke is drawn.

A group’s or a layer’s own fills and strokes, which paint every member, are not stitched as shapes of their own. They give StitchCraft effects their thread and stroke (below), with SC-W0807.

Effects. StitchCraft’s live effects are kept in the object’s appearance as {"id": "plugin.dev.stitchcraft.<family>", "params": {…}, "visible": true}. The family is stroke, satin or fill (stitchcraft_params::Family). An object with visible StitchCraft effects is stitched as they say, in their order, instead of by its paints. A fill effect fills the object’s shape, a stroke effect stitches along it and a satin effect makes a satin column of it. With this rule, an object sews what its effects say and nothing else. Each effect is sewn on the shape as it is drawn. VectorCraft draws an effect after the first on the stitches of the one before, though, so the preview of an object with 2 is not what is sewn, and SC-W0807 says so, once for an object and once for a group. A fill with an outline takes 2 objects: the shape with a fill effect, and a copy pasted in front of it (Edit › Paste in Front) with a stroke effect. The record’s parameters are the element’s. A number is written as a decimal, a toggle as true or false, a choice as its id and a list as its values with spaces between. What the record leaves out takes its default, as in the plug-in’s dialog. The thread is the colour of the topmost fill VectorCraft draws for a fill, and of the topmost stroke for the others, falling back on the other kind. An opaque paint comes before one of opacity under 1, which lets what is under it show. A stroke or satin effect follows the width and join of that stroke, or a width of 0 when none is drawn. VectorCraft writes a stroke of paint none for an object without one, which it doesn’t draw. A satin column too narrow to stitch across is sewn as a stroke, with SC-W0212. SC-W0807 names a zigzag 0 mm wide. VectorCraft’s own effects change what an object draws, and are left out with SC-W0807 (Object › Expand Appearance makes paths of what they draw).

A group’s effects (REQ-VC-006). VectorCraft runs a group’s or a layer’s geometry effects on each path and compound path inside it, however deep, with the group’s bounds as their frame (reshape_leaves in crates/effects, 0.7.0 to 0.12.0), and paints what they return with the path’s own paints. The group’s own paints paint the shapes inside it as its effects and those of the groups around reshaped them (evaluate_container). They go over its contents. The Contents row of its Appearance panel (contents_index) is last in the list by default, and the paints listed under it go under the contents. StitchCraft’s live effects are geometry effects, and applying a graphic style to a group puts its effects and paints on the group. So each path inside sews as the group’s StitchCraft effects say, and as the preview shows it. A name can leave one out (commands). Its thread and stroke come from the paints over it, the topmost first, as for an object’s own paints. The groups’ paints over their contents come first, the outermost first, then the object’s own, then the groups’ paints under their contents, the innermost first. The same order applies to an object’s own effects, which VectorCraft paints with its own paints, under the groups’ paints over the object’s shape. A path that neither its own paints nor a group’s paint is invisible, and is left out without a word.

A clip group’s first object is its clipping object. VectorCraft paints a path, a compound path or text there with its own paints alone (clip_paint in crates/doc): its fills under the clipped art and its strokes over it. A group’s effects run on such a path too. After Make Clipping Mask it has no paint, and sews nothing. VectorCraft draws nothing of a group or an image there, which an imported file can have, and neither is sewn. Where StitchCraft effects meet from more than one level, a path’s own and a group’s, or 2 groups’, VectorCraft draws one effect run on the stitches another drew, which a machine cannot sew. The path sews as the nearest effects say, and SC-W0807 names it. A path’s own Auto effect inside a group with an Auto effect is SC-W0920 instead (names of shapes).

Clip groups (REQ-VC-017, M8.7). A group or a layer whose kind has "clip": true clips what it holds to its first object, the clipping object. Object › Clipping Mask › Make wraps the objects selected in such a group, the topmost first, which must be a path, a compound path or text. It takes that object’s paints and effects away, and marks a path "clipping": true (clip_make in crates/engine). The Layers panel’s Make Clipping Mask clips a layer or a group the same way. VectorCraft clips to the clipping object’s area whatever its paints, hidden or not (Node::clip_shapes in crates/doc, read at 0.19.0, and alike from 0.13):

  • A path’s area is the one its fill rule fills, and a compound path’s is its paths’ together, by its own rule, holes and all.
  • A nested clip group’s is its own clipping object’s.
  • Another group’s or a layer’s is that of its members that show, together, but a Shaper group’s sources.
  • Text’s is its glyphs’ outlines, an image’s or a placed document’s its frame, and a live object’s what it draws. A guide or a symbol doesn’t add to it.

One shape keeps its rule, several are united, and a clipping object of none hides the group’s contents. The adapter makes the clipping object’s area into a clip of each element made inside the group, however deep, as the SVG adapter does with a clip path (Element::clips). Clip groups inside one another give one clip each, and the engine cuts an element to all of them (REQ-GEN-005). It cuts a fill’s area and a stroke’s lines, each piece sewn on its own. Satin columns are sewn whole, as in Ink/Stitch (SC-W0217), and an element wholly outside its clips isn’t sewn (SC-W0013). An automatic shape is cut before it is digitized. The clipping object isn’t cut to its own clip, as VectorCraft paints its fills inside its own area and its strokes over the clip’s edge. The clips round its group do cut it.

The adapter doesn’t read glyphs, frames or what a live object draws. Text, an image, a placed document, a live object or a kind it doesn’t know adds nothing to the clip, and SC-W0807 names it, with the VectorCraft command that makes paths of it, such as Type › Create Outlines. A path in the clipping object whose geometry can’t be used doesn’t add to the clip either, and SC-W0808 names it. A clip left with no shape cuts away all of what it clips, where VectorCraft shows what lies in the glyphs or the frame.

VectorCraft runs a group’s geometry effects on every path inside it, the clipping objects of the clip groups it holds among them (for_each_leaf in crates/effects), and clips to what they return. Where StitchCraft’s effects apply to a clipping object, the preview is cut to the stitches they draw of it, a fill’s rows or a stroke’s line. What sews is cut to the clipping object as it is drawn, and SC-W0807 says so. Its hint is to apply the effects to the objects the group clips.

Ids. An element is vc:<object id>:<what>: fill or stroke for a paint, with its rank among the object’s fills or strokes from the second on (fill.2), and the family for an effect. VectorCraft keeps an object’s id when it saves, so a report and a preview name the same object. A repeated id gets ~2, ~3, … as in the SVG adapter.

Reports. SC-E0806 refuses a file that isn’t a VectorCraft document, or is larger than the adapter reads. SC-W0807 names what isn’t stitched. SC-W0808 names geometry that can’t be used, such as a number that doesn’t read or a point more than 10 m from the origin, and a shape that draws nothing. SC-I0809 lists the layers and guides left out because VectorCraft doesn’t print them, and SC-I0811 the objects and layers left out by their names. The compatibility gate will have each VectorCraft version it tests write files for the adapter to read back (Level B, M6.6).

A gradient’s geometry

A linear gradient fill made in VectorCraft sews the linear gradient of the object’s topmost fill that paints, in stitch export and in StitchCraft Fill’s live effect alike (REQ-VC-022, M10.12). VectorCraft’s gradient paint keeps its colours apart from where it lies: {"type": "gradient", "gradient": {"kind", "stops"}, "geom"?, "angle"}. Its geom gives the start and end in the document’s coordinates, in points, which the reader turns into millimetres. VectorCraft fits a gradient without one to its object each time it draws it. The fitted gradient runs through the middle of the object’s bounds round its curves, at angle counter-clockwise as the canvas shows it. It is as long as the bounds are across that way. The reader fits it alike, charging the budget for each segment it measures (GradientGeom::fit in VectorCraft’s crates/color, read for 0.17.0 to 0.21.0, and paint.setGradientGeom in its docs/mcp.md).

Each stop’s offset is kept from 0 to 1 and never before the stop before, and its opacity from 0 to 1, 1 where the file leaves it out. Its colour converts as a solid paint’s does, and one that doesn’t read is black, with SC-W0807. A stop’s midpoint moves where VectorCraft draws the 2 colours half mixed, which rows of whole colours can’t follow, and SC-W0807 names a midpoint other than half way. A gradient more than 10 m from the origin is named too, and the fill sews its first colour. A radial or freeform gradient, and one of one stop, is sewn in its first colour, as other fill methods sew a gradient. A fill without a linear gradient fades its own colour out (SC-W0329).

Decision: the Test Sheet filter draws gradients. A filter’s output may hold gradient paints in the native format’s form, geom among them, which VectorCraft clamps and keeps (its docs/plugins.md, Output). So Test Sheet draws a linear gradient fill with its gradient as a gradient paint, its geom in points, and the document sews as the sheet’s design (apps/stitchcraft-vc-plugin/src/testsheet/tests.rs). Rejected: a solid paint of the first colour, which would sew the fade of SC-W0329. A gradient without its geom was rejected too: VectorCraft would fit it to the object’s bounds at its angle, not where the sheet puts it. The filter draws TS-17B, which holds gradients from M10.12, and its draw-every-sheet case sews them as the sheet does.

Lettering

M14.4 sews a text object in an embroidery font (REQ-VC-026, REQ-VC-027). Fonts describes lettering itself, and fonts built into the plug-ins where a plug-in finds a font.

A text object as a plug-in gets it, read in VectorCraft v0.24.1 (docs/plugins.md, crates/doc/src/text.rs and crates/plugins/src/effect.rs of its source):

Plug-inWhat it is given of text
ExporterThe whole document. A text object has its runs, with their characters and character styles, and its kind, its transform and its effect records
Filter that lists inputs: ["type"], from API level 2The selected text, read only: its runs, its paragraphs’ styles and its transform
Live effectThe object’s outlines as one path, with its paints. The text is not among them

No plug-in is given a font’s data or a glyph’s outlines. An exporter can read the text and can’t outline it, so M14.4 sets it in a font of StitchCraft’s own. A live effect can’t even read the text, so it can’t draw the embroidery font before export (RFC, P6).

The setting is an effect on the text. StitchCraft Lettering (<ns>.lettering) is a live effect that a person applies to a text object. Its record keeps the font’s name and lettering’s settings, and its run returns the geometry it was given, as hello does. 2 other ways were weighed:

  • A filter that replaces the text by lettering’s shapes. The text could no longer be retyped, and the shapes are satin columns that mean nothing as art.
  • A name kept with the document, by the Design Settings filter. One font would serve every text, and a text’s settings would lie far from it.

With the effect the text is still a text object. Retyping it changes what sews, the Appearance panel shows the effect and opens its dialog, and the exporter finds the record on the object it belongs to.

The dialog is generated from lettering’s own settings (stitchcraft_svg::lettering::SETTINGS), each with its default and help, by Ink/Stitch’s names. It has 10 rows, which fit VectorCraft’s dialog without sections:

RowSettingDefault
Fontfont, a textempty, which is small_font
Sizescale, in percent of the font’s size100

Letter, word and line spacingletter_spacing, word_spacing, line_height, in millimetres0

The 2 settings that place a text along a path are left out, since a text object sews at its own place.

The font is a text field, where a list of the fonts built in was the other choice. A font is named by its folder, as Ink/Stitch finds it, or by the name of its font.json, in any case. A list would make the effect’s manifest differ between a build with fonts and one without, and VectorCraft checks a record’s value against the manifest installed. A document would then lose its font in a plug-in built with other fonts. A name also reads the same from the command line. The dialog’s help names the default font, and an export that doesn’t find a font names those it has.

Text without the Lettering effect

From M14.7 a text object under automatic digitizing sews without the effect too (REQ-VC-029), as a text object in automatic digitizing does. A text is under automatic digitizing in the cases a path is:

  • The text has the Auto effect.
  • The text has no StitchCraft effect of its own, and the nearest group or layer around it that has StitchCraft effects has the Auto effect and no stitch effect.
  • The document is read with --auto, or without a switch, as a document is by default, and neither the text nor a group or a layer around it has a StitchCraft effect.

A stitch effect says how a path sews and means nothing for a text. A text with one, its own or a group’s around it, is left out as before.

The adapter reads horizontal point type. Its lines are the lines of its characters. The first starts at the origin of xf, and each next line lies a leading further down. The leading is the character style’s leading, or 1.2 times its size when it sets none, which is VectorCraft’s automatic leading. The size, the leading, the fill and the typeface’s name are those of the first run that has characters, so a text of several sizes sews at its first. The paragraph’s justify anchors each line at its start, its middle or its end, and a justified paragraph is anchored at its start. xf turns the lines as it turns the baseline, and scales the size and the leading as it scales across the baseline. A size that doesn’t read is 12 points, and SC-W0807 says so. The document states no length for a line, so each is fitted to an estimated one. Area type, type on a path and vertical type are left out with SC-W1111, as they are with the Lettering effect.

Only a plug-in that is given the text can do this:

WhereA text automatic digitizing reaches
File › Export to PES or DST, and the browser demoSews in the font built into the exporters
stitch export and stitch planSews in the default font of the folder STITCHCRAFT_FONTS names
The Auto effect’s own run, which draws the stitches on the canvasIs given the text’s outline as one path, and digitizes that as a shape. So the canvas doesn’t show what the export sews

What the adapter reads. A text object’s kind holds its runs, its transform xf and whether it is point type. The adapter joins the runs’ characters, in order, and lettering splits the lines at line feeds. An inline graphic’s character is left out and said (SC-W0807).

  • Place. Point type’s origin is the start of its first baseline, and that is the origin of a text lettering sets. The text is turned as xf turns the baseline. The size is the effect’s scale, since an embroidery font sews only within its own heights, so the scale of xf and the screen font’s size aren’t used. A mirrored or slanted text sews turned only (SC-W0807).
  • Thread. A font that sews in one thread sews in the colour the text’s first characters are filled with, and a font of several colours keeps its own.
  • Clips. The clips around the object cut the letters, as they cut a path’s elements. As a clip group’s clipping object a text is left out, as before.
  • What isn’t set. Area type wraps its lines by the screen font’s widths, and type on a path follows its path by them. An embroidery font has other widths, so neither can sew where VectorCraft draws it. Vertical type needs glyphs drawn to sew downwards. Each is left out with SC-W1111. M14.3’s lettering along a path could take type on a path in a later step.
  • What is said. The warnings of lettering and of the font’s reader are passed on, a font’s once however many texts name it. Their notes for information aren’t, since they are said of every glyph. stitch lettering prints them. A message that names the fonts found names 8 and counts the others.
  • Other effects on the text, and the screen font’s attributes, change what VectorCraft draws and nothing that sews.

Before export the text looks as VectorCraft draws it, in its screen font. Nothing on the canvas shows the embroidery font, its size or its width. The user page says so, and gives the font’s height in millimetres for a scale. When the text can’t sew, the export says SC-W1111: the font isn’t found, with the fonts that are, or the text is of a kind that isn’t set. VectorCraft shows a declined export’s message without its warnings, and a document of one text whose font is missing has nothing to stitch. So a declined export says its first SC-W1111 after its error.

The layer edge. The adapter sets the text itself, so that the plug-in and stitch share one reader. It depends on stitchcraft-svg, where lettering and the font reader are, beside it in layer 3. The edge is listed in xtask/src/layers.rs. The other choice was a second copy of the placing in each app.

Browser distribution

M6.13 publishes VectorCraft’s web editor with StitchCraft’s plug-ins on the project’s Pages site. The work came from crowecawcaw’s pull request #260. Try StitchCraft in your browser says what a visitor sees, web/README.md how to build it, and the docs pipeline how it is published.

The editor and its release

web/build.py builds the editor with Trunk from VectorCraft’s source at a release, and doesn’t change it. It writes 2 folders. The app is the editor with the plug-ins, and the demo folder is the plug-ins, the loader and the starter patch without the editor.

compat/vectorcraft.toml records the release beside the gate’s pins, as a tag and the commit the tag names, and the build stops when the tag names another commit. The release is the stable track’s, from 0.24 on: the loader calls uiInspect and docInspect, which VectorCraft’s page has from that release. A test fails when the demo’s release is older than the stable track’s.

The loader touches VectorCraft only through the calls its page offers as window.vectorcraft. VectorCraft documents them in its docs/control-protocol.md, under “In the browser”. The loader installs each light module with plugin.install and opens the starter drawing with document.open. It doesn’t install the heavy filters, which VectorCraft installs only once a person allows it, and the page offers them as files.

Trunk runs without the network. The workflow installs Trunk and the 2 tools Trunk would otherwise download, wasm-bindgen and wasm-opt, each checked against a checksum kept in the repository (.github/actions/tools/action.yml).

The editor is built once for each state of what it is built from. web/build.py keeps the built editor in target/web/editor under a key. The key is a SHA-256 of 4 things: the release as compat/vectorcraft.toml records it, rust-toolchain.toml, the versions of Trunk, wasm-bindgen and wasm-opt in .github/actions/tools/action.yml, and web/build.py itself. A build that finds an editor under its key copies it and builds only the plug-ins, which are always this revision’s. web.yml keeps that folder in the Actions cache under the same key, with the runner’s system before it, and restores no other key. So a pull request that changes the release, the compiler, a tool’s version or the build script builds the editor, and every other round takes it from the cache.

A kept editor is not checked against a checksum, because 2 builds of it don’t give the same bytes. What protects it is where a cache may come from. GitHub gives a run the caches written on its own branch and on main, and a run for a pull request writes to that pull request’s own scope, a fork’s too. So the editor that main publishes was built by a run on main, from code that was merged, and no pull request can put another under its key.
